## 1. Что именно строим

Job Agent — самостоятельная облачная программа для поиска работы. По расписанию она ищет вакансии из нескольких источников, сохраняет их, убирает повторы, оценивает по явным критериям, показывает пользователю короткий список и учитывает его решения. Затем она помогает готовить отклики и следить за результатами. Отправка отклика и другие внешние действия, требующие человеческого решения, выполняются только после явного одобрения пользователя.

Нынешний Gmail → Google Sheet pipeline продолжает работать до переключения. Его перенос — одна из интеграций Job Agent, а не цель всего проекта. Новая система должна находить полезные вакансии и без LinkedIn alerts.

## 2. Где что находится

- **Java 21 / Spring Boot приложение** — логика Job Agent: поиск, нормализация, оценка, рекомендации, действия и API. В разработке запускается локально, в рабочем режиме — в AWS. Это один и тот же код.
- **PostgreSQL** — единственный master для новой системы после переключения: вакансии, компании, оценки, решения, заявки, запуски. JSONB хранит исходные ответы источников и версии AI extraction.
- **S3** — приватные CV, документы и созданные версии CV. В базе — ссылки на объекты и история версий, сами файлы в Git не попадают.
- **EventBridge Scheduler** — запускает агента по расписанию в AWS, без включённого MacBook. Начальный кандидат: Пн/Ср/Пт, время согласуем перед включением.
- **AWS compute** — запускает Java-программу. Lambda или ECS/Fargate выбираем по фактическому времени работы, сетевым требованиям и полной цене, прежде чем создавать платные ресурсы.
- **CloudWatch, IAM, secret storage, backups** — наблюдаемость, ограниченные права, токены и восстановление.
- **Google Cloud OAuth registration** — только способ один раз выдать Java-программе разрешение на Gmail. Программа и база в Google Cloud не размещаются. Текущий доступ ChatGPT к Gmail остаётся у старого pipeline; новому AWS-приложению понадобится собственное разрешение.

House Agent в будущем использует общие платформенные решения, но его доменная логика и расписание остаются отдельными. Сначала делаем работающий Job Agent; не строим абстрактную платформу вместо продукта.

## 3. Один проход агента

1. Запуск получает `run_id` и набор включённых источников.
2. Адаптеры источников находят вакансии. Первый набор выбираем после проверки доступных официальных API/feeds и карьерных страниц целевых работодателей. Gmail/LinkedIn alerts — дополнительный адаптер. Не предполагаем, что любой сайт разрешает автоматический сбор.
3. Сохраняем исходный payload, URL, время обнаружения и версию адаптера.
4. Приводим название роли, работодателя, место, тип работы и требования к общей схеме. Дедуплицируем по стабильным ID/URL и затем по проверяемому fingerprint.
5. Правила исключают очевидно неподходящие вакансии. Облачная LLM оценивает остальные по заранее заданным критериям, сохраняет баллы, аргументы, модель/версию prompt и исходные факты. При ошибке LLM запись остаётся для повторной оценки.
6. Строим короткий список: ссылка, причины «за/против», неопределённости, рекомендуемое следующее действие. Пользователь отмечает интересно/неинтересно и причину.
7. Обратная связь меняет правила/критерии контролируемо и позволяет сравнивать качество новых версий. Никаких самостоятельных откликов.
8. Для Gmail-сообщения: сначала завершить обработку и подтвердить commit в PostgreSQL; только потом пометить письмо обработанным, прочитать и архивировать. Неудавшееся Gmail-действие сохраняется для безопасного повтора.

## 4. Архитектура кода и репозиториев

На старте один Git-репозиторий `job-agent` с модульным приложением и инфраструктурой как кодом. Отдельный репозиторий для общей платформы создаём, когда второй агент действительно начнёт использовать общие компоненты; преждевременное выделение усложнит первую поставку.

Модули/пакеты приложения:

- `source` — адаптеры поиска и Gmail, исходные payload и provenance;
- `vacancy` — нормализация, работодатели, вакансии, дедупликация;
- `evaluation` — критерии, LLM gateway, версии prompt, оценки;
- `review` — shortlist, решения и обратная связь пользователя;
- `career` — структурированный профиль и ссылки на приватные документы;
- `application` — черновики, явное одобрение, история отправки;
- `outcome` — ответы, интервью, предложения и результаты;
- `run` — расписание, идемпотентность, журнал ошибок и очередь внешних действий;
- `infra` — миграции БД, конфигурация AWS и развёртывание.

Минимальные API после появления пользовательского интерфейса: получить shortlist; открыть вакансию с оценкой и исходным URL; сохранить feedback; просмотреть историю запусков; позже — создать черновик отклика, одобрить или отклонить его, записать outcome. Для scheduled запуска HTTP-контроллер не обязателен. UI можно сделать позже; первый обзор может быть через простой защищённый отчёт, но способ доставки утверждаем до подключения персональных данных.

## 5. Данные по мере развития

Первая миграция: `agent_runs`, `source_items`, `processed_messages`, `employers`, `vacancies`, `vacancy_sources`, `external_actions`. Уникальные ключи на source ID и action idempotency key. Не полагаться на название компании как единственный идентификатор.

Затем: `evaluation_criteria`, `vacancy_evaluations`, `review_feedback`, `searches`, `shortlists`. После подтверждения потребности: `career_profiles`, `skills`, `experience`, `projects`, `certifications`, `education`, `languages`, `documents`, `cv_versions`, `applications`, `outcomes`; позже embeddings/pgvector. Версии raw payload и extraction сохраняем для повторной обработки.

Далее отдельные PR для feedback, Gmail OAuth, импорта/сверки, cutover и каждого следующего продукта. После каждого merged PR обновляем Career Board по фактам и записываем проверяемый материал для CV, LinkedIn и интервью в `CAREER_EVIDENCE.md` и Narrative. Публикаций автоматически нет.

## 8. Критические правила

- Один master для старого pipeline до cutover; в тестовой БД возможны только изолированные копии, которые не запускают реальные действия.
- Секреты и личные документы не попадают в Git. CV и Arbeitszeugnisse попросить у пользователя после готовности и проверки приватного S3-хранилища.
- Перед любым внешним действием сначала подтверждать запись состояния. Для заявок требуется отдельное явное одобрение пользователя.
- Не выдавать запланированное за сделанное. Публичные карьерные истории только по проверенным PR/тестам/результатам; коммерческие сведения не переносить.
- Ориентир «несколько евро в месяц» пока не проверен. Нельзя обещать эту стоимость до регионального расчёта, включающего минимальную цену БД, хранение, сеть, логи и резервные копии. Избегать ненужного NAT Gateway.
