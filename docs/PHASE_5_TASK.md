## Scope and local checks

The Java 21 batch image is built for `linux/amd64` using digest-pinned Temurin build/runtime images, Maven Wrapper, a non-root runtime user, a minimal build context and exec-form Java entrypoint. The normal command has no mode and only checks PostgreSQL/Flyway. The `cloud-app` profile validates migrations without applying them. The separate migrator task applies migrations before normal tasks run. SIGTERM reaches Java directly; Spring closes its context and Hikari pool on ordinary exit. Abrupt termination cannot guarantee a graceful shutdown, so use ECS task stop timeouts and verify them during deployment. Process exit codes, including PARTIAL=2, are Java's exit codes.

Local commands from the repository root:

```sh
./mvnw -B clean verify
docker buildx build --platform linux/amd64 -t job-agent:phase5a-local --load .
export TF_DATA_DIR="$(mktemp -d)" # isolate offline initialization from the configured remote backend
terraform -chdir=infra/terraform init -backend=false -input=false
terraform fmt -check -recursive infra/terraform
terraform -chdir=infra/terraform validate
unset TF_DATA_DIR
git diff --check
```

These checks need Docker and provider downloads but no AWS credentials. The Terraform data source for an orderable Aurora configuration is checked only in an account-backed plan. CI repeats the application tests, container build and offline Terraform checks without AWS credentials.

### Aurora prolonged-activity warning (deployed; delivery test verified)

The owner reports `MinCapacity=0`, `MaxCapacity=2`, `SecondsUntilAutoPause=300` on `job-agent-p5a-db`. Writer metric `ServerlessDatabaseCapacity` was 0 ACU throughout 2026-10-31 21:13–21:18 Europe/Berlin, evidence of **initial idle auto-pause**. No application execution and subsequent wake/sleep cycle has been tested. [AWS documents](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html) that the **instance-level** metric reports zero while paused and [uses the `DBInstanceIdentifier` dimension](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-administration.html). The alert targets only the Terraform writer instance, not the cluster. It evaluates twelve 5-minute periods of `Minimum > 0` (12 of 12), or approximately one hour of nonzero capacity. It does not identify why the writer is active or whether a job has completed. CloudWatch may use a wider evaluation range, and metric publication/evaluation and SNS delivery add delay; one hour is not an exact wall-clock deadline. `treat_missing_data="missing"` leaves absent telemetry unknown/`INSUFFICIENT_DATA`, not zero or proof of sleep. [CloudWatch's missing-data rules](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html) also mean a recovery (`OK`) notification reports alarm state, not necessarily a verified pause. Both `ALARM` and `OK` changes notify the same topic; `INSUFFICIENT_DATA` does not notify.

The owner confirms the subscription and a controlled ALARM state test delivered an email; a metric-driven return to OK delivered another. These tests do not prove a real one-hour trigger. The topic policy permits `SNS:Publish` from the exact alarm ARN and account via the CloudWatch service principal. It carries alarm metadata only and does not configure SNS server-side KMS encryption; adding customer-managed encryption requires a separate key policy and cost review. The email subscription requires an explicit confirmation link from AWS; Terraform creation alone does not activate delivery. Create the ignored local `infra/terraform/activity-alert.auto.tfvars` and set `aurora_activity_alert_email` to the owner's single confirmed address. Do not commit that file, paste the address into chat, or put it on a command line. The address is personal data and is stored as an SNS subscription endpoint in remote Terraform state even though the variable is marked sensitive; protect the state and saved plan. Review the fresh plan for **only** the topic, policy, subscription and alarm before applying. After an authorized apply, confirm the subscription email, then verify `Confirmed` status in SNS. The owner can test notification delivery without waking the database using `aws cloudwatch set-alarm-state --region us-east-1 --alarm-name job-agent-p5a-writer-prolonged-activity --state-value ALARM --state-reason 'Owner notification test'`; check the email and CloudWatch alarm history. The alarm automatically returns to its metric-derived state, often within seconds, potentially sending an `OK` recovery email. This is a notification test, not a capacity or auto-pause test; do not use SNS `Publish` as proof of CloudWatch policy or alarm action. [AWS documents `SetAlarmState` for this purpose](https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/API_SetAlarmState.html). That test has now been reported by the owner, not repeated in this local preparation.

The [CloudWatch price example](https://aws.amazon.com/cloudwatch/pricing/) is about **$0.10 per month** for one standard-resolution metric alarm in us-east-1 before any applicable free allowance or credits. [SNS pricing](https://aws.amazon.com/sns/pricing/) includes request and email-delivery allowances; low notification volume may add no charge within them, but exceeding allowances, other usage and taxes depend on actual billing. This increment adds no recurring compute. Existing $5/$10 budget emails and this warning neither stop AWS spending nor set a hard cap. Email delivery does not guarantee that the owner notices or acts on it. The cost sketch below predates this alert and excludes its potential charge.

## Monthly cost sketch, us-east-1, before credits

This sketch covers only the Phase 5A foundation and a hypothetical manual batch cadence, **not the complete Phase 5 architecture or its operating cost**. Illustrative 730-hour month: 13 manually started 20-minute 1-vCPU/2-GB Fargate tasks, 13 DB active periods of 25 minutes at average 0.5 ACU, 10 GB Aurora Standard storage, one million I/O requests, three secrets (RDS-managed master, migrator, app) retained for a month, 1 GB S3, 1 GB ECR and 0.1 GB ingested logs. Task duration and DB auto-pause are assumptions, not observed behavior. Rates must be verified in an account-backed calculator before apply.

| --- | --- | ---: |
| Aurora compute | 5.42 h × 0.5 ACU × $0.12/ACU-h | 0.33 |
| Aurora Standard storage and I/O | 10 GB × $0.10; 1m × $0.20 | 1.20 |

| **Phase 5A priced subtotal** | Excludes items described below and later Phase 5 resources | **about $3.13+** |

If the DB fails to pause and stays at 0.5 ACU for 730 hours, its compute alone is about **$43.80/month**, putting the same foundation subtotal around **$46.60+/month**. Scaling to 2 ACU, frequent restarts or a second writer would cost more. Temporary restore testing adds a second cluster's compute/storage, snapshot storage beyond included allowance, task/network use and possibly public IPv4; estimate its duration before the drill. The configured one-day automated backup has a shorter restore window than the original seven-day design; retained final/manual snapshots and excess backups can be charged. An internet gateway has no standing hourly fee; data transfer, request/I/O and any later endpoints do. No NAT Gateway is included. Additional unpriced foundation usage includes the Terraform state bucket, S3 requests and versions, CloudWatch log storage/queries, Secrets Manager API calls, data transfer/egress, extra Aurora I/O and backup/snapshot storage. Future Phase 5 SQS, schedules, the activity alarm prepared in this branch, restore exercises, deployment automation and any added networking have **no estimate in this subtotal**.

For the **priced Phase 5A assumptions only**, the estimated final AWS payment is **$0 if all usage is credit-eligible and sufficient credits actually apply**; otherwise the payment is the uncovered actual charges. After credits expire, the estimated final payment for this same narrow scenario is **at least about $3.13/month with reliable pausing, or $46.60/month if the DB stays at 0.5 ACU**, plus the unpriced usage above. These figures are not a full operating-cost quote. Anthropic/Tavily spending is external and is **not** offset by AWS credits. ## Recovery and teardown

No restore drill or measured recovery target exists. Deletion protection and Terraform `prevent_destroy` guard the cluster, writer, ECR and private bucket. A deliberate teardown needs a reviewed plan, explicit disabling of protection, confirmation that no task or pilot claim is active, export/retention decisions, a final RDS snapshot and manual cleanup of retained ECR images, bucket versions, snapshots, secrets, logs and state. Storage and secret charges continue until those resources are actually removed. Never use an unreviewed `terraform destroy` as a cleanup shortcut.
