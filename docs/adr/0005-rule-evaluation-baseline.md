# ADR 0005: Deterministic rule evaluation baseline

Date: 2026-10-27. Status: Phase 4A implementation for review.

Phase 4A uses an explicit private JSON profile file outside Git. It contains a profile ID and version, title terms for preferred and reserve role families, work country, acceptable hybrid locations, arrangement/title exclusions and an optional soft salary preference. The committed example is fictional. Validation rejects missing/oversized/malformed files and invalid fields. A SHA-256 hash of the deserialized, consistently serialized profile is stored with the `(profile_id, version)` key; a changed profile under the same key fails and requires a new version. The database stores identifiers and hashes, not the profile or salary target. Do not place a real profile, redirected shortlist output or private values in the repository.

Policy `rules-v1` matches configured literal title terms at word boundaries. It does not infer a person's skills from a job requirement. Explicit configured title/arrangement exclusions and a nonconflicting source country exclusion yield `EXCLUDED`; an unknown role, missing work eligibility or contradictory country evidence yields `NEEDS_REVIEW`. `SUITABLE` requires a configured role match and explicit synthetic structured evidence that permits the configured country. A country-scoped remote statement ranks before EU remote with explicit work-country permission; an allowed hybrid location ranks next. Rank is an ordinal preference, not a probability or model confidence. Missing salary does not exclude; a comparable amount below the optional preference adds an explanation only. Unsupported currency or period remains unknown. No exchange conversion is inferred.

Live Greenhouse/Lever workplace labels, titles, descriptions and locations are untrusted source facts. The policy normalizes supported arrangement labels (`remote`, `hybrid`, `onsite`, Lever's `on-site`) to `REMOTE`, `HYBRID` or `ONSITE` before applying explicit arrangement exclusions; it preserves the original source label as evidence. Unsupported labels remain unknown. A `remote` label or mention of a country never confirms permanent work-country eligibility. This first baseline recognizes confirmed eligibility only from the synthetic `evaluationEvidence` fixture contract used in tests; live vacancies therefore normally need review until a later trusted evidence workflow exists. Supporting excerpts are bounded and provenance retains the original source URL. Raw pages, complete profiles and salary targets are not included in shortlist output. No external content is executed.

Flyway V9 stores a small profile version registry and append-only vacancy evaluations. Identity combines vacancy ID, a SHA-256 revision of current normalized content/source provenance, profile ID/version/hash and policy version. The revision includes the selected source-item ID, and the evaluation row retains that source-item foreign key. The latest linked source snapshot whose content digest matches the accepted vacancy digest is selected by source-item ID; an older, rejected observation cannot replace accepted content as evaluation evidence. A newer matching snapshot invalidates an older evaluation even when its normalized text is unchanged. The evaluation service rejects ambient transactions. It registers the profile in a short transaction before processing, then owns a separate short transaction per vacancy: it locks the vacancy row, reads source provenance, applies the rule and inserts a single evaluation under a database unique constraint. A failed insertion rolls back that vacancy's evaluation; earlier committed vacancies and the profile registration remain. Concurrent identical evaluations serialize on the row and cannot duplicate. A profile registration check rejects the same ID/version with changed criteria. Evaluation reads at most 100 IDs per page and at most 500 per invocation; the caller uses the returned cursor for another batch.

Shortlist retrieval reads bounded pages and keeps at most the requested top results in memory, with a maximum output limit of 50. It includes only evaluations whose revision, profile hash/version and policy version still match the current vacancy. Suitable and needs-review groups are separate. Within each group, working-arrangement rank comes first, then persisted role classification (`PREFERRED` before `RESERVE`, then `UNMATCHED` for review), then vacancy ID. No score weights are applied. This is a per-row read snapshot: a concurrent source change after a row is checked can make a just-printed entry stale; a later report rechecks it. Previous evaluations remain as history. The command is an explicit batch entry point. Event-driven evaluation, LLM assessment, richer verified evidence, user fit, cloud delivery and action approval are later work. Existing ingestion/outbox transactions are unchanged.
