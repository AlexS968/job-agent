# ADR 0009: Bounded SQS transport for existing outbox events

Status: decision implemented; diagnostic AWS smoke completed on 2026-11-04 and one bounded rules evaluation smoke on 2026-11-06. The owner reports one controlled two-profile batch and two delivered emails on 2026-11-08, then enabled the recurring schedule. Its first run is due 2026-11-10 and remains unverified. The revised report and security-updated image are merged but not deployed; see the [public-safe architecture](../PHASE_5_AWS_ARCHITECTURE.md).

## Decision

Use one gated SQS standard queue and one DLQ for the existing `VacancyDiscovered`/`VacancyUpdated` v1 envelopes. PostgreSQL remains the source of vacancy and outbox state. The message contains `eventId`, `eventType`, `schemaVersion`, `aggregateId`, `occurredAt` and `runId`; it contains no vacancy description or private source payload. A consumer checks the envelope against the persisted outbox row, including its historical event identity, without reading the latest vacancy revision to reinterpret it.

The one-off producer uses the existing database claim, two-minute lease, claim token and three-attempt cycle. It releases the database transaction before `SendMessage`. Only a confirmed send changes the outbox state to `PUBLISHED`; this state means transport acceptance, **not** handler completion. An uncertain send is retried under the existing bounded policy, so duplicate SQS messages are possible. A lost database acknowledgement after a successful send likewise permits a later duplicate. Failed outbox cycles need the existing explicit replay.

The one-off diagnostic consumer validates type, version, identifiers and persisted payload identity. It commits a `(consumer_id, event_id)` receipt and a diagnostic `sqs_vacancy_observations` row in one PostgreSQL transaction, then deletes the SQS message. The handler identity `sqs-vacancy-diagnostic-v1` includes its version. Database uniqueness prevents concurrent duplicate effects. A handler error or failed delete leaves the message for visibility expiry and the source queue's three-receive DLQ policy; a failed delete may follow a successful database commit, so redelivery must find the existing receipt and skip the effect. The diagnostic row proves only local transport processing, not vacancy evaluation. The separate evaluation handler below is explicitly selected; no schedule or paid provider call is enabled.

The source queue uses SSE-SQS, TLS-only policy, four-day retention, 120-second visibility and ten-second long polling. The DLQ uses SSE-SQS, TLS-only policy, seven-day retention and `byQueue` redrive allowance for only this source queue. Producer and consumer have separate one-off task roles scoped to send and receive/delete respectively; the regular app role remains without SQS permissions. Standard SQS is at-least-once and may deliver duplicates or reorder messages. The receipt is the database-level idempotency boundary, not an exactly-once network guarantee. Local ElasticMQ tests exercise compatible queue behavior. The [AWS smoke record](../PHASE_5_SQS_RUNBOOK.md#observed-aws-smoke-2026-11-04) confirms one synthetic publish/process/duplicate cycle and invalid-message redrive; it does not establish sustained reliability or real evaluation.

The DLQ smoke used one application rejection followed by manual receives to reach the configured redrive threshold; it did not test three application failures. Separate `sqs-status` verification was not run. At that diagnostic milestone, the owner deferred the image's PCRE2 assessment; the later local remediation is merged but not deployed or ECR-verified.

## Rules evaluation consumer and bounded AWS smoke

The explicitly selected `--mode=sqs-evaluate` task uses the existing `rules-v1` evaluation service and a private profile injected as a Secrets Manager secret. Its versioned handler identity includes the complete profile criteria hash, so a different profile version/criteria set has a separate receipt namespace. It makes no LLM/search request. The original diagnostic consumer and its receipts remain intact.

New vacancy events retain envelope schema 1 and add `source_item_id` and the existing rules revision hash to the persisted outbox payload in the ingestion transaction. This is an additive payload extension; older schema-1 events lack a snapshot and are rejected by the business consumer without acknowledgement. The producer still sends only the identifier envelope. The business consumer validates the envelope against the stored event, then locks the current vacancy and checks both source ID and revision. A superseded event records a `STALE` receipt/effect without evaluating newer content under the old event ID. The evaluation service creates or reuses the current rules evaluation and links it to the event in `sqs_evaluation_effects`. Receipt, evaluation and effect link commit together; SQS delete follows commit. A failed transaction leaves no receipt. Lost delete can redeliver but cannot repeat the committed effect. A distinct profile may be evaluated by an explicit replay of the same envelope; there is no automatic replay of historical events or diagnostic messages.

The [2026-11-06 evaluation smoke](../PHASE_5_SQS_RUNBOOK.md#verified-rules-evaluation-smoke-2026-11-06) used a synthetic demo profile: one Solaris event produced evaluation ID 1 and an exact-envelope redelivery reported a duplicate with the same ID. It did not evaluate all imported vacancies or personal suitability. No schedule or complete batch pipeline was exercised. At that smoke milestone, the ECR findings remained deferred; the later local remediation is merged but not deployed or ECR-verified.

The scheduled-batch preparation reuses this transport and `rules-v1` handler without changing SQS receipts. V17 builds on V16: one durable Berlin-date invocation owns two profile-specific report rows. The queue is consumed once under DE without requesting a shortlist; bounded direct evaluation sweeps register both profiles and cover current stored vacancies before either shortlist is selected, including historical vacancies with no pending event. Direct sweeps retain the existing vacancy lock, current source revision and profile/version evaluation identity, but do not manufacture SQS receipts or claim to process historical event revisions. Import and outbox writes retain their existing transaction boundaries. The AT report uses `EVALUATION_SWEEP` when no backlog remains and does not claim a second import or queue pass. SNS state is independent per profile; a confirmed DE email cannot be replayed because AT fails, while ambiguous publication requires manual review. The [schedule runbook](../PHASE_5_SQS_RUNBOOK.md#scheduled-reports-and-controlled-aws-run) covers disabled-by-default deployment and failure paths. SNS acceptance is not exactly-once inbox delivery.
