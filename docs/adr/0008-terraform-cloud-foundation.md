# ADR 0008: Reviewable Terraform foundation for one-off AWS batches

Status: Phase 5A merged in PR #24 and one-day backup correction in PR #25. After historical Free Plan failures, the owner changed to Paid Plan and reports the private Aurora cluster/writer deployed. Initial idle auto-pause and Aurora alert email delivery were observed. Phase 5B bootstrap completed, but the first migration task failed during startup; application wake/sleep, a real one-hour alert trigger and restore remain untested. The retry is documented in the Phase 5B runbook.

## Decision

Use Terraform 1.17.1 and AWS provider 6.71.0 for a small us-east-1 baseline. Terraform supplies a reviewable plan before deployment and leaves room to change deployment providers later without a multi-cloud abstraction. Pin the provider in `.terraform.lock.hcl`. The baseline uses public ECS task subnets with temporary public IPv4, private Aurora subnets, no NAT Gateway, load balancer, ECS service, RDS Proxy, reader, or schedule. A single Aurora PostgreSQL 17.11 Serverless v2 writer is configured for 0–2 ACU and 300-second auto-pause. The original seven-day retention failed during the owner's Free Plan apply, before any Aurora cluster/writer was created. The one-day correction merged in PR #25. A subsequent Free Plan error required Express configuration; the owner then changed to Paid Plan and reports that the private cluster and writer were deployed. This reduces the point-in-time recovery window; a restore drill and any longer snapshot strategy remain pending. Initial idle auto-pause was observed for five minutes at 0 ACU; an application wake/sleep cycle and migration compatibility remain deployment gates. Offline validation cannot establish them.

An ECR image digest and separate application/migration DB secret ARNs are required before Terraform registers task definitions. The default task command only checks the database. The `cloud-app` profile validates Flyway history without migrating; a separately run migration task uses the migrator role. No task definition is registered by the default `enable_runtime=false` configuration. Application task IAM grants no AWS actions. ECS execution IAM is limited to image pull, its log group and the supplied DB secrets. Secrets are not passed through Terraform as values. This does not mean Terraform state is secret-safe: any later resource input that contains a password or token can enter state even if marked `sensitive`.

Use a separately bootstrapped, encrypted/versioned/private S3 state bucket with the S3 backend `use_lockfile=true`. Bootstrap is an explicit later action. Local `.tfstate`, plan files and private tfvars are ignored. Never apply the baseline using local state and then casually switch backends; migrate state under review.

The public us-east-1 RDS CA bundle is bundled in the image and JDBC uses `sslmode=verify-full` with that trust file. Refresh the bundle before expiry/rotation. Aurora also sets `rds.force_ssl=1`. The application and migrator must not use the managed master user. Role provisioning is a separate controlled bootstrap inside the VPC after cluster creation and before enabling runtime; its credentials and the two JSON secrets are not in this repository.

The low-cost baseline uses AWS-managed RDS storage encryption and S3 SSE-S3 rather than customer-managed KMS keys. Outbound task traffic is limited to TCP 443 on public addresses and TCP 5432 to the private DB security group, but the 443 destination range is broad because ECR, Secrets Manager and CloudWatch endpoints are not pinned and VPC endpoints would add standing cost. A local Trivy scan flags the lack of explicit customer-managed keys and broad HTTPS egress; these are reviewable cost/security tradeoffs, not evidence of a clean security scan. Narrow egress or use priced VPC endpoints before expanding task permissions or enabling live providers.

## Consequences

The owner reports that network, S3, ECR, ECS cluster, IAM, Aurora cluster and writer are deployed. Preserve remote Terraform state; review a fresh plan for each later change, and never reuse saved plans. No application task or restore test is verified, so there is no proven autonomous workload or recovery guarantee. Persistent Aurora storage once created, snapshots, ECR, S3 versions, Secrets Manager and logs can incur charges even when no task runs and the DB pauses. `prevent_destroy`, RDS deletion protection and a final snapshot require deliberate, reviewed teardown. SQS, schedules, OIDC deployment, tested restore, private-document handling and pilot-spending continuity are later increments. Cloud LLM calls remain disabled until the existing pilot accounting is reconciled; a fresh database must not mint a new allowance.
