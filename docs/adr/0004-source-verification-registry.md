# ADR 0004: Source verification and activation

Date: 2026-10-26. Status: implementation contract for Phase 3C.2.

An unverified URL is only a candidate. A caller may supply at most five URLs per invocation with an origin label (`owner-confirmed`, `independently-reviewed` or `manual-candidate`). The previous Tavily pilot did not persist its 34 URLs. Verification does not call Tavily and does not store search snippets or full pages. `independently-reviewed` means the operator inspected an employer-controlled website and its career-page link separately from search results before invoking verification; the CLI cannot establish that trust root on its own.

An owner-confirmed or independently reviewed official employer domain is the trust root. A candidate without one remains `MANUAL_REVIEW`, including a working ATS API URL. For a trusted domain, the verifier fetches one HTTPS career page on that exact domain and inspects bounded HTML links. A direct link from that page to one recognized Greenhouse or Lever identity is association evidence. HTTP 200, page titles, search snippets, ATS reachability and display names are not ownership proof. Zero links require manual review; multiple distinct supported identities, contradictions or aggregators require manual review. Unsupported ATS platforms are `UNSUPPORTED`. Network failures are `RETRYABLE_FAILURE`, not rejected ownership. Invalid or unsafe input is `REJECTED`. Technical ownership does not establish role fit or work-country eligibility.

The fetcher permits HTTPS on port 443 only, no userinfo, IP literals or non-public DNS answers. Its Apache HttpClient connection manager resolves through a validating DNS resolver at connection time and connects only to those returned addresses; the original hostname remains the request authority and TLS certificate hostname. Redirects and transparent decompression are disabled; the verifier validates same-host redirect targets before another request and records cross-host redirects for manual review without requesting the new host. Three requests, five seconds, 256 KiB per response and 200 links per page bound one candidate. HTML is parsed with jsoup only after content-type and byte checks. No JavaScript, forms, credentials or cookies are sent. An invocation admits at most five candidates. Network work completes before any registry transaction.

The registry key is `(platform, region, source_id)`, never employer display name. V8 adds a `source_verification_decisions` row is keyed by the lowercase official employer domain and stores the latest trusted observation at PostgreSQL microsecond precision, its decision, evidence hash and last accepted ATS identity. The verifier captures and truncates observation time before HTTP. In a short persistence transaction it inserts the domain row if absent, locks it with `FOR UPDATE`, and orders results before changing any source row. This serializes a newer negative decision ahead of an older positive even when no source row exists yet. Source identity uniqueness and the locked source row arbitrate competing positive claims from different domains; a negative observation for a different domain does not, by itself, refute an existing domain-to-source association. HTTP never runs under these locks. Repeated evidence may deduplicate its attempt row, but a later trusted observation still advances the decision time. V8 reconstructs the latest trusted decision and last accepted association from existing V7 attempts and registry rows, and deactivates any older source contradicted by that decision; V7 remains unchanged.

A later different ATS identity for the same official domain is a sticky conflict; a board replacement needs separate manual review. A fetched page with no supported link or only an unsupported platform sets the domain decision and any matching source to `UNVERIFIED` and deactivates it. A strictly later positive observation of the same association can restore `VERIFIED`, but remains inactive and needs explicit activation. Time-based expiry sets `STALE`; a later positive for the same domain and identity also restores `VERIFIED` without reactivating. Even if expiry has not yet been materialized, a verification after the 30-day window does not preserve an old active flag. Ambiguous or conflicting ownership/evidence, including different evidence at the same stored microsecond, sets a sticky `CONFLICT` domain decision and/or `MANUAL_REVIEW` source state. Subsequent automatic verification cannot clear these states. No manual conflict-resolution command is implemented in this increment; an operator must review and resolve the data in a separate controlled workflow. Older observations cannot advance the decision or restore eligibility. Untrusted claims, invalid input and transient network failures do not advance the domain decision or invalidate an existing association.

An evidence fingerprint and candidate URL identify an observation. Identical repeat observations do not add rows. A new observation can refresh a source only if it is later than the stored observation and the domain decision permits recovery. Equal-time contradictory evidence and another employer-domain claim enter sticky manual review and deactivate the source; no silent transfer or automatic conflict clearance occurs. Older observations cannot deactivate newer evidence. Invalid input and claims without a trust root do not invalidate prior evidence; a successfully fetched but contradictory or unsupported official-page observation does. Transient fetch failure leaves a still-current source untouched. Evidence remains current for 30 days. Activation is a separate explicit transaction and rechecks verified state and freshness. Import rechecks active, verified and fresh state immediately before delegating to the existing Greenhouse/Lever batch service. A concurrent state change after this short check can race with the outbound fetch; this increment does not hold a database lock during HTTP. Verification never imports vacancies or dispatches outbox events.
