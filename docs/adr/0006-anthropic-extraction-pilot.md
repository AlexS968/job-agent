# ADR 0006: bounded Anthropic vacancy evidence pilot

Status: implementation merged in PR #15; two live attempts failed validation and a subsequent v2 attempt succeeded on 2026-10-29. The v3 skill-evidence contract, section-context correction and vacancy-12 evidence-decoding correction are merged. Partial-result handling merged in PR #22; no live request was part of it.

## Contract

Explicit extraction uses selected public vacancy fields only: title, location, description, source workplace type and salary. No private profile, CV, tools, browsing or credentials enter the prompt. Vacancy text is untrusted data. Claims carry fact, value, supplied source field, bounded supporting quote and uncertainty. Missing claims are UNKNOWN. A matching quote is evidence of a source statement, not legal permission or personal fit. Generic remote labels, EU references, office addresses and country mentions cannot confirm work-country permission. A positive permission claim is `STATED` only when its quote covers an entire source sentence matching one of the narrow unconditional employer-statement forms; negated, conditional, partial and ambiguous wording remains `UNCERTAIN`. This lexical check is deliberately conservative and is not unrestricted semantic validation or legal verification. Single-valued contradictory facts remain `CONFLICTING`. Quote matching uses NFC, case folding and whitespace collapse. `rules-v1` and shortlist behavior remain unchanged. Manual reference labels, not Sonnet output alone, will measure pilot quality.

Work identity contains vacancy ID, source snapshot ID, vacancy/source revision, provider/model and prompt/schema/policy versions. The exact selected input fields are retained as JSONB with the work item so quotations can be reviewed against the actual supplied snapshot after a vacancy row changes. Identical successful work is reused. Comparison uses Sonnet only after Haiku success on the same revision and input. Results stay separately reviewable; no automatic event or evaluation is created.

## Accounting and recovery

V10 stores the pilot budget, global in-flight claim, work and attempts. The owner approved a revised contract: USD 2 target spending for the entire pilot, USD 3 maximum authorized expenditure, at most 30 distinct primary Haiku revisions and 10 Sonnet comparisons, with no automatic top-up, fallback or expansion. USD 3 is authorization, not a billing guarantee. Live execution requires an API key, explicit command opt-in and same-day review of pinned pricing. Three owner-run primary Haiku requests occurred on 2026-10-29. All were charged in application accounting; the first two outputs were rejected and the third passed structural validation.

Before HTTP, the application serializes the complete request (including system prompt, schema, source fields, output limit and thinking setting). It estimates input tokens as twice the UTF-8 request bytes plus 8,192 tokens for provider-injected schema/system overhead, then prices 2,048 output tokens including thinking. The owner raised the complete request limit from 12,000 to 24,000 UTF-8 bytes for a broader technical sample; response bytes remain capped at 100,000 and HTTP duration at 20 seconds. Haiku uses its higher long-context tier: $0.50/M input and $2.50/M output. Sonnet uses $2/M input and $10/M output. Cache writes, if reported despite no caching being requested, use the conservative one-hour 2x multiplier; reads use at least the base input price. All accounting uses integer micro-USD. These margins are conservative estimates, not verified upper bounds: Anthropic says token counting is approximate and structured output injects billable prompt material. An unexpectedly large bill remains possible after submission. This transport-size change does not alter prompt, schema or policy versions, so historical work identities and results remain unchanged.

The reservation transaction locks the single budget row, requires no active claim or spending halt, and admits a proposed estimate only if accounted spending plus outstanding reservations remains within USD 2. It records one global active work/token and commits before HTTP; no database lock spans the request. At most 80 attempts and three per work item are permitted. Reported usage reconciles `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and `output_tokens`. Valid observed usage is recorded even when it exceeds the reservation or USD 3; any excess over the reservation durably halts new requests. Without valid usage, the full reservation remains, including refusals or uncertain transport outcomes. The accounted amount is known cost plus outstanding reservations; observed cost is reported usage only. Neither measure includes other account activity, taxes, adjustments or billing lag.

The durable global claim survives lease expiry, crash and uncertain acknowledgement; it cannot silently admit another request. An input exceeding the request byte limit is rejected before HTTP. A response exceeding the response byte limit is different: consumption is cancelled after submission, so provider completion and billing are unknown. It is recorded as `UNCERTAIN`, keeps the full reservation and global claim, and blocks other work. The source adapter and extraction gateway share a bounded HTTP body subscriber, while their callers retain their distinct failure classifications. A controlled recovery requires a 60-second age, operator confirmation that no provider request remains in flight and billing review. It releases the global slot but keeps the uncertain reservation, event identity and attempts. Replay is a separate explicit action and may bill again; exactly-once external execution is not claimed. A spending halt cannot be cleared by ordinary recovery. Claim-token fencing rejects stale completion. HTTP never holds a database transaction; ambient transactions are rejected. Failure-tracking errors are suppressed under the original request failure, and PostgreSQL outage can prevent tracking. Pre-interrupted work stops before reservation. Cancellation after reservation but before submission retains the full reservation; the gateway checks cancellation immediately before submission. Once submitted, cancellation can race with billing. The owner should review provider billing and available workspace monthly spend controls separately; no exact per-pilot provider hard cap has been verified or configured.

The supplied input was retained and consists of public title, Berlin location and the Greenhouse description, which includes HTML-escaped markup and entities. Entity encoding could contribute to a quote mismatch, but is not a confirmed explanation for this response. Work 1 is `FAILED`; attempt 1 is `INVALID`, with 3,648 input tokens and 916 output tokens. Application accounting records 4,114 micro-USD observed and accounted against a 17,004 micro-USD reservation. This is reported usage priced by the application, not independent provider billing confirmation. The active claim and halt are null. No validated facts were stored from the first attempt.

V11 adds per-attempt validation claim index (zero-based; `-1` for root errors), a fixed failure category and an optional rejected output artifact. Only a response received before a validation failure can be retained, and only when its complete UTF-8 content is at most 16,384 bytes. Larger content is omitted rather than truncated. The artifact is stored in local PostgreSQL, never in `result_json`, logs or Git; it remains untrusted data and is never treated as a validated claim. No automatic retention purge is implemented, so local database access and lifecycle must be controlled. The historical first response remains unavailable because V10 did not store it. Diagnostics do not relax exact quotation, source-field or country-permission checks. A new provider response would require a separately authorized paid request; this diagnostic work does not authorize one.

A second owner-run request on 2026-10-29 retained its 1,761-byte rejected response. Attempt 2 reported 3,648 input and 736 output tokens, with 3,664 micro-USD observed/accounted cost. Zero-based claim 9 used `SALARY_PERIOD` value `annual gross`, quoting `The annual gross salary range for this position is:` from the supplied description. Schema v1 constrained `fact` but left `value` unconstrained, while the validator accepted only `YEAR`, `MONTH`, `DAY`, `HOUR`. This is the confirmed contract mismatch. Schema v2 uses supported `anyOf` and `enum` constraints for arrangement and salary-period values; the prompt v2 states the canonical values and exact-substring evidence rule. The validator still checks all fields and maps only an `annual gross` value with a matching quoted phrase to `YEAR`. Other unsupported or ambiguous periods remain invalid. The policy is versioned `pilot-v2`, so old v1 work cannot be reused as v2 output. The complete retained response passed v2 validation offline with 10 claims and no further validation failures; this is structural/evidence validation, not an independent assessment that every inferred fact is correct. Neither historical failed attempt was updated. Before and after offline diagnosis, the canonical budget remained 7,778 micro-USD observed/accounted, two attempts and one distinct primary revision, with no active claim or halt. Provider billing is not independently reconciled; no new paid call was made.

## Skill evidence contract under local review

A later owner-run v2 primary extraction succeeded for the same vacancy/snapshot. The canonical database then showed three attempts, 11,552 micro-USD accounted/observed, two distinct primary work identities, and no active claim or spending halt. Manual review found a supported `Java or Golang` mention classified as `REQUIRED_SKILL` solely from text under “We'd love to see”; mandatory status is not established. Other skill and competency statements were omitted. Passing quote validation did not establish semantic accuracy or completeness.

The merged v3 contract replaces `REQUIRED_SKILL`/`PREFERRED_SKILL` with a `SKILL` claim. `value` is an exact substring of its supporting quotation and preserves the employer's alternative wording; `skillEvidence.kind` distinguishes technology from competency, and `requirementStrength` is `REQUIRED`, `PREFERRED` or `UNKNOWN`. Exact `quote`, optional preceding `sectionQuote` and optional `strengthQuote` must be substrings of the same supplied field. A nonempty section quote must precede the claim. For an explicit HTML heading, its scope continues until the next heading; plain text still uses a 1,200-character bound. Only narrow, unconditional full-statement forms or an explicit relevant section heading support a non-unknown strength. Negated, conditional, shortened, isolated and contradictory wording remains `UNKNOWN`; “We'd love to see” is ambiguous. The validator deliberately rejects other phrasing rather than attempting unrestricted semantic interpretation. The deterministic validator checks quotations and conservative strength cues; it does not independently prove semantic equivalence between every skill label and its quote.

The v3 prompt requests distinct supported skills and competencies within the unchanged output/request budget, without splitting alternatives into independently mandatory items. The v3 validator requires exactly `claims` and a boolean `truncated`, matching the provider schema; it rejects `true` and 24 or more claims. Historical v1/v2 JSON is deserialized separately and is not revalidated as v3 output. Provider `max_tokens` stop reasons already fail closed. A model can still omit facts while declaring `truncated=false`, so completeness requires manual sampling. Versions `evidence-v3/schema-v3/pilot-v3` create new work identity; v1/v2 history, attempts and budget remain untouched. A new primary identity consumes an additional pilot slot even for the same vacancy. Rules-v1, shortlist, salary and country-permission policy remain unchanged. The first v3 live sample is documented below; any further paid sample requires a separate owner decision.

## First v3 live attempt and offline diagnosis

The retained claim's value was `driving cross-functional initiatives`, while the exact source quotation says `The ability to drive cross-functional initiatives while balancing technical and product priorities.` The source says `drive`, not `driving`. The quote is present in the stored input; the value is a paraphrase, so strict skill-value validation correctly rejects it. No stemming or semantic equivalence rule is added. An exact-value correction such as `drive cross-functional initiatives` is a possible future provider output, not a rewrite of the failed response.

Offline validation of every retained claim found two additional section-context failures at indexes 11 and 12. Both quote text under the same escaped HTML heading `We&#39;d love to see`; the heading-to-quote distances are 1,221 and 1,371 normalized characters, exceeding the old 1,200-character cutoff, with no intervening heading. Policy `pilot-v4` uses the actual HTML heading boundary for these claims while retaining the distance limit for unstructured text. Prompt `evidence-v3` and schema `schema-v3` are unchanged; the policy version changes work identity so historical v3 attempts cannot be silently reused under the revised validator. The original retained response still fails at claim 10. A temporary offline copy with only claim 10 changed to the exact source substring validates all 13 claims under policy v4; this does not validate the historical response or establish semantic accuracy. No historical output, work, attempt or budget is modified. At the read-only check, attempts totalled four, primary-distinct work three, accounted/observed spending 18,257 micro-USD, and the active claim and halt were null. ## Vacancy-12 offline failure diagnosis

The owner-run vacancy-12 primary attempt on 2026-10-29 stored work 4 and attempt 5 as `FAILED`/`INVALID`, with claim index 5 and `SKILL_SECTION_NOT_SUPPORTED`. Its exact input is source snapshot 12, revision `8102b40c16e0fbefda3db5b1aa257865a445fcf0c10b136591bbed461debf538`. Claim 5 says `Java`, quotes `read, review, and debug code in multiple modern languages (e.g., Java, Go)`, and points to section `We'd love to see`. The source contains that quotation once at raw offset 3,865, under `&lt;h4&gt;We&#39;d love to see&amp;nbsp;&lt;/h4&gt;` at offset 2,531. The next heading is `Benefits` at offset 5,965. The prior validator required the decoded section quote to occur literally in the escaped source, causing a false rejection. No repeated quote occurrence caused this failure.

An offline claim-by-claim audit found the same false section rejection at indexes 5, 6, 7, 8 and 10. Indexes 9 and 11 were also falsely rejected because their visible quotations cross inline spans or contain decoded `&quot;` entities. Policy `pilot-v5` decodes the escaped HTML and text-entity layers for evidence matching, removes only inline formatting tags, and retains heading and block tags. A quote must still occur exactly in that visible text; skill values must still be exact substrings of their quotations. Section heading boundaries and the 1,200-character unstructured-text bound remain. Prompt and schema versions stay `evidence-v3/schema-v3`. The policy change creates a new work identity; historical attempts and successful v2 output are not rewritten or reused under the new validator.

After this correction, claim 8 still fails `SKILL_STRENGTH_NOT_SUPPORTED`: `German is a plus` is understandable as a preference, but `is a plus` is outside the deliberately narrow `PREFERRED` wording in the current prompt and validator. Claims 9 and 12 still fail `SKILL_VALUE_NOT_IN_QUOTE`: their values add `design` and `experience`, respectively, which are not exact substrings of their supporting quotations. These are provider-output contract violations, not evidence-decoding defects. The complete retained response still fails; no rejected output was promoted to validated facts. Offline revalidation of the earlier vacancy-15 retained response still rejects only its paraphrased claim 10. The first vacancy-15 response remains unavailable. At the read-only check on 2026-10-30, the canonical budget showed 25,076 micro-USD accounted/observed, five attempts, four distinct primary identities, zero comparisons, and no active claim or halt. Further live sampling needs separate review, a current pricing guard and an explicit owner decision; this diagnosis made no paid call or database change.
Claim 0 uses `Berlin` for `ONSITE` but marks its uncertainty `UNCERTAIN`; it therefore does not confirm an onsite arrangement. Claims 1–4 quote the stated annual gross salary range and EUR currency. Claims 5 and 6 separately name Java and Go from the same `e.g., Java, Go` example; both are UNKNOWN-strength evidence, but a reviewer should retain the employer's example grouping rather than treat either as an individual requirement. Claims 7, 10 and 11 have exact visible evidence and unknown strength. These observations are a manual audit, not a validated result or a complete accuracy benchmark.

## Partial-result contract merged in PR #22

Policy `pilot-v6` changes validation and work identity while retaining `evidence-v3/schema-v3`. Invalid JSON, invalid root/truncation metadata, reported truncation, 24 or more submitted claims, provider refusal and incomplete generation remain fatal for the entire response. A well-formed complete response validates each submitted claim independently. Only expected `ExtractionValidationException` claim violations are isolated; unexpected internal errors remain fatal. Accepted claims alone enter `result_json`. Rejections retain their original zero-based indexes and fixed safe categories. The attempt may retain the original rejected response only under the existing 16,384-byte UTF-8 cap; no unbounded provider response or extra source payload is stored.

`SUCCEEDED` means all submitted claims passed and at least one claim exists. `PARTIAL` means at least one accepted and at least one rejected claim. `FAILED` means no accepted claim or a fatal response failure. An empty, well-formed claims array is `FAILED` with `EMPTY` attempt outcome: it is not useful evidence or proof of completeness. A response whose every claim is rejected is `FAILED` with `NO_VALID_CLAIMS`. A completed provider response, including `PARTIAL` and these no-valid-claim outcomes, reconciles returned usage and releases global ownership only after the completion transaction succeeds. Underestimated usage still records observed cost, halts the pilot and keeps the claim for controlled recovery. Transport uncertainty, cancellation and lost acknowledgement retain their existing fencing and recovery rules.

V12 stores accepted/rejected counts and bounded rejection index/category metadata on new work and adds `PARTIAL` to the work status constraint. New columns default to zero/empty for old rows; no historical status, result, attempt, rejected artifact or budget value is rewritten. A completed `PARTIAL` result is reused without another request; it is not automatically retried and cannot qualify a Sonnet comparison. `FAILED` work follows the existing explicit invocation and attempt-cap rules. `extract-status` exposes counts/categories, and a live batch invocation exits 0 for `SUCCEEDED`, 2 for `PARTIAL`, and 1 for `FAILED` or fatal errors. A status inspection remains read-only and exits 0. Neither acceptance nor a `truncated=false` declaration proves semantic accuracy or completeness. Validated claims do not feed `rules-v1` or external actions. The separate extraction-aware evaluation policy in ADR 0007 can select compatible current validated results for its shortlist.

Cross-claim checks run after individual validation. Skill identity for this check uses NFC normalization, whitespace collapse and case folding; it compares the complete value, so `Java or Go` and `Java` remain distinct. Accepted `REQUIRED` and `PREFERRED` claims for the same normalized skill both retain their original quotations, but their requirement strengths become `UNKNOWN` and their claim uncertainty becomes `CONFLICTING`. Repeated consistent strengths and an `UNKNOWN` claim alongside one explicit strength do not create a conflict. `SUCCEEDED` still means all submitted claims passed validation; it does not mean every accepted fact is certain. The conflict marker persists in the validated result and survives reuse.

An accepted country permission is downgraded to `UNCERTAIN` when a rejected opposite country claim for the same value still has an exact source-field quotation. An accepted non-UNKNOWN skill strength becomes `UNKNOWN` with claim uncertainty `UNCERTAIN` when a rejected claim for the same skill has an exact quoted value. Rejected content is a conservative reason to withhold certainty, never a confirmed fact. Unsupported or unquoted rejected claims cannot create this uncertainty. Broader semantic contradiction detection still requires manual review rather than pretending lexical validation proves truth.

Read-only offline application of the v6 validator to retained responses would accept 10 and reject 3 claims for vacancy 12 (indexes 8 `SKILL_STRENGTH_NOT_SUPPORTED`, 9 and 12 `SKILL_VALUE_NOT_IN_QUOTE`), and accept 12 and reject 1 claim for vacancy 15's v3 response (index 10 `SKILL_VALUE_NOT_IN_QUOTE`). Neither retrospective result was persisted or relabeled. Vacancy 12 still has a generic `ONSITE` claim marked `UNCERTAIN`; Java and Go are separate UNKNOWN-strength examples from one source phrase, not established individual requirements. The earlier vacancy-15 v1 response lacks the current root fields, so v6 rejects its root; historical contract results are not reinterpreted or overwritten. These counts describe syntactic/evidence validation only, not owner-approved accuracy labels. No paid request or canonical database write occurred in this increment.
