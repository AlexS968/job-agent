# Phase 6A: protected vacancy page and source yield

Phase 6A.1 is deployed: the owner signed in, loaded the protected DE/AT page and opened an original posting link. The first vacancy request failed and a later request succeeded; its cause is unknown. This is observed behavior, not evidence that Aurora wake-up caused the failure. The shell and OAuth configuration are public assets; vacancy data requires an API Gateway JWT access token and membership in the `job-agent-owner` Cognito group. Cognito Lite uses its classic hosted UI, a password and required TOTP. The browser uses authorization code with PKCE, keeps its access token only in memory and does not log or store profile JSON. The API also checks owner-group claims. No signup route is provided.

**MFA prompt limitation (Phase 6D review):** the deployed Lite pool requires TOTP, and [Cognito's classic hosted UI manages its MFA prompt](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa-totp.html). The owner reported “Please enter the code from 592970.” [Cognito's verification API](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_VerifySoftwareToken.html) accepts a friendly device name, but read-only pool metadata cannot establish whether that number is a saved name or text supplied by the hosted UI. Device tracking is disabled, so `AdminListDevices` returns a configuration error rather than TOTP-label metadata. No safe Terraform or page-text correction is established. The owner can compare the prompt with the authenticator entry and contact AWS support for clarification while keeping the working TOTP factor; do not reset or delete it without a separately reviewed recovery path.

The page switches between `alex-de` and `alex-at` and reads current `rules-v1` evaluations. It shows suitable and needs-review preferred/reserve roles, an employer name, original HTTPS posting link, explicit reason codes and unknown conditions. It excludes synthetic source namespaces, stale source snapshots and unmatched roles, matching the existing report shortlist's trusted-source boundary. Only the newest registered version per profile is shown; if its sweep is incomplete, older-version rows are not mixed in. A profile without evaluated vacancies shows an empty list. This is a stored-evidence view, **not** a fresh evaluation, a country-permission confirmation, a new source of truth or a claim of personal suitability. Pages are capped at 20 rows, offset at 1,000 and JSON at 64 KB. Larger result sets require a later reviewed pagination design.

The existing Aurora PostgreSQL 17.11 Serverless v2 writer in us-east-1 supports the deployed Data API. [A Data API read can resume a paused writer](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html), so browsing can incur Aurora compute and the page does not promise a zero-cost read. The Lambda has no VPC attachment, NAT or database socket and has `ExecuteStatement` on this cluster plus `GetSecretValue` on one dedicated reader secret. The reader role has column-level SELECT grants, no writes or raw payload access. The existing app/migration roles and batch schedule remain; the result email is combined.

A source snapshot change makes an older evaluation ineligible for the current view. The current page query cannot independently recompute a normalized-content revision if that content changes without a new source snapshot; a full sweep is required after such a change.

Shortlisted means role-relevant SUITABLE/NEEDS_REVIEW with confirmed country location. Stored-vacancy counts can overlap between sources; one vacancy can also be evaluated for both profiles. The cross-source overlap count identifies linked vacancies shared by active sources. The window is all stored history as of each read, not the complete platform or a country-wide job market. These counts cannot explain why the owner did not apply before feedback exists. ## Phase 6A.3 deployed combined result email

V19 retains V17's historical DE/AT rows and SNS identities. It adds one result-publication slot per Berlin date and per-profile item identities for that publication. A scheduled run still imports and consumes the queue once, then sweeps the stored vacancies independently for DE and AT under `rules-v1`. Only current, trusted-source, role-relevant evaluations with confirmed country evidence enter notification selection. The protected page continues showing the full current shortlist. The combined email has one short subject with the Berlin date and distinct new-vacancy count, separate DE/AT counts for new and newly relevant vacancies, and the reviewed protected HTTPS page URL; it sends even when all counts are zero. Error and launch-failure alerts remain separate.

For each profile, the stable notification identity is `(profile_id, vacancy_id)` in a **successfully published** combined result. Once reported, a routine source revision, profile-version change or country-policy change does not make that vacancy new again. V19 still stores the current revision, profile version/hash and evaluation/country policy as provenance. On the first result for a profile without V17 history, current eligible vacancies form its initial new set. On later runs, a vacancy first eligible for that profile is **new** only when its earliest stored source observation was created after the last successfully published combined result; if it was already stored, it is labeled **newly relevant**, including after an eligibility, profile or policy change. This distinguishes discovery from a later match but cannot establish when a job first appeared on the external platform. A vacancy newly stored and eligible for both profiles counts once in the subject and once in each country section. Unpublished PREPARED/PUBLISHING/UNCERTAIN rows do not establish a delivered notification. V17 emails lack complete per-item identities: on the first combined publication, current candidates for any profile with a historical PUBLISHED email become a conservative baseline rather than being called new. This can omit genuinely new items that arose since the old email; the email says so and points to the full page. V17 rows are never replayed or deleted.

Preparation of the body and item identities commits together before SNS. PUBLISHING commits before the single SNS call outside the transaction; a confirmed message ID moves the combined row to PUBLISHED. An ambiguous SNS outcome becomes UNCERTAIN; a crash or failed database acknowledgement can leave PUBLISHING. All unresolved states block automatic publication on later dates until reviewed recovery, and a completed Berlin-date slot never republishes. Even PREPARED is blocked for review because automatic recovery is intentionally absent. SNS acceptance is not inbox delivery. The 24-minute cooperative deadline remains inside the 25-minute watchdog; a blocking operation may outlast the cooperative deadline. No automatic resend is provided for uncertain publication.

## Phase 6B deployed owner feedback

On 2026-11-15, an unauthenticated feedback POST returned 401 and the owner reported that one Germany decision with a fixed reason remained visible. No Austria write was exercised because no Austria vacancy was available. This is bounded AWS evidence, not verification of every feedback path.

V20 adds append-only `review_feedback`. Each row stores a unique request UUID, stable vacancy ID, displayed evaluation ID, DE/AT profile ID and version, source revision, owner decision/reason and recording time. An owner can choose `INTERESTED` without a reason; `NOT_INTERESTED` requires one of `ROLE_MISMATCH`, `SENIORITY`, `LOCATION_OR_WORK_COUNTRY`, `REMOTE_POLICY`, `SALARY`, `TECH_STACK`, `COMPANY_OR_BUSINESS_MODEL`, `OTHER`; `NEED_MORE_INFO` requires one of `WORK_COUNTRY_UNCONFIRMED`, `SALARY_UNKNOWN`, `REMOTE_POLICY_UNKNOWN`, `ROLE_DETAILS_UNKNOWN`, `OTHER`. No comments are stored. A reason is the owner's judgment, not confirmed source evidence, and does not change criteria or the agent's evaluation. Later choices append rows; the latest choice for a vacancy/profile appears beside the current evaluation, marked when it refers to an earlier evaluation. The original HTTPS source link and evaluation evidence remain visible.

The existing JWT plus owner-group check guards both routes. A separate `POST /feedback` Lambda has a dedicated secret and database role: narrowly scoped current-evaluation SELECT, feedback INSERT/SELECT and identity-sequence USAGE; no table UPDATE/DELETE or raw source-payload SELECT. The page Lambda retains its read-only secret and receives only feedback projection columns. The server checks exact JSON fields, decision/reason combinations, UUID, profile, IDs, version and revision. Its parameterized `INSERT ... SELECT` accepts only a currently displayed, trusted-source, country-confirmed evaluation for that profile/version; a stale or forged combination inserts nothing. A repeated UUID with identical fields returns the existing row, while reuse for a different decision fails. After an uncertain HTTP result, retry the same selection/request UUID; the browser keeps it only in memory, never local storage. A reload with no confirmed response requires checking the latest card state before a new decision. No database secret, access token or private vacancy text is logged.

## Phase 6C deployed shortlist-quality explanation

On 2026-11-15, the owner applied the reviewed Terraform plan: one `/quality` route was added, two Lambda functions were updated and nothing was destroyed. Unauthenticated `GET /quality` returned 401. After sign-in, Germany showed 22 distinct stored vacancies, one role-relevant and one shortlisted; Austria showed 22, one and zero. The Germany view retained the owner's need-more-info/salary-unknown decision. Each view showed only its selected country's source diagnostics. These are observed results for the stored sample, not counts of an entire job platform or country. Non-owner access, every example link and the ordinary Tuesday/Thursday scheduled run were not verified by these checks.

The owner-protected `/quality` read uses the selected DE or AT profile, current `rules-v1`/`country-v1` evaluations, active verified sources and the latest decision per vacancy/profile. It counts distinct stored vacancy IDs once across sources. Its mutually exclusive stages are unevaluated, unmatched role, excluded, country unconfirmed, shortlisted and other; role-relevant and shortlist totals are shown separately. Explicit exclusion reasons are counted across every current `EXCLUDED` evaluation, including those in the unmatched-role stage. Unknown conditions are separate. These evidence counts may overlap and are never added to the funnel. At most three HTTPS posting examples per stage are shown from current evaluations. All stored observations from currently active verified sources form the window, as of the database read. This is not a platform-wide vacancy count; one vacancy can appear under multiple sources or both profiles.

Latest owner choices and fixed reasons are counted over distinct stored vacancies for the selected profile, independently of agent decisions. Missing feedback is not an application outcome; applications are not tracked. The page displays the feedback denominator and warns when fewer than ten vacancies have decisions. The version check inspects the two latest registered profile versions and their criteria hashes, current source `input_version` counts, and evaluations on the same vacancy, source item, revision, `rules-v1` and `country-v1` policy. Multiple evaluation variants for either version are excluded as ambiguous. It reports both version-cohort sizes, matched vacancies and those with a latest owner decision tied to each evaluation. If there is no prior version, unchanged criteria, fewer than ten matched vacancies, fewer than ten paired decisions, or more than 1,000 stored vacancies in the bounded comparison sample, it reports that specific limit rather than a trend. Otherwise it reports only descriptive counts of `INTERESTED` decisions on the paired cohort, never a causal improvement. Different source-processing versions are shown as sample composition, not compared as equivalent cohorts; extraction-version effects are not isolated. Historical evaluations and feedback are preserved. The page reader uses its existing column-level SELECT grants; no additional grants are needed. The API remains JWT- and owner-group-protected, with a 64 KB response bound. Source-level `/yield` is filtered to the selected profile. No batch, email or feedback-write behavior changes.
