# Phase 6A.1: owner-only vacancy page (locally prepared)

This increment adds a browser sign-in shell and a read-only API over the existing `vacancies`, `source_items`, `evaluation_profiles` and `vacancy_evaluations` tables. It has **not** been deployed or checked in AWS. The shell and OAuth configuration are public assets; vacancy data requires an API Gateway JWT access token and membership in the `job-agent-owner` Cognito group. Cognito Lite uses its classic hosted UI, a password and required TOTP. The browser uses authorization code with PKCE, keeps its access token only in memory and does not log or store profile JSON. The API also checks owner-group claims. No signup route is provided; the owner must create and assign the one intended user privately.

The page switches between `alex-de` and `alex-at` and reads current `rules-v1` evaluations. It shows suitable and needs-review preferred/reserve roles, an employer name, original HTTPS posting link, explicit reason codes and unknown conditions. It excludes synthetic source namespaces, stale source snapshots and unmatched roles, matching the existing report shortlist's trusted-source boundary. Only the newest registered version per profile is shown; if its sweep is incomplete, older-version rows are not mixed in. A profile without evaluated vacancies shows an empty list. This is a stored-evidence view, **not** a fresh evaluation, a country-permission confirmation, a new source of truth or a claim of personal suitability. Pages are capped at 20 rows, offset at 1,000 and JSON at 64 KB. Larger result sets require a later reviewed pagination design.

The existing Aurora PostgreSQL 17.11 Serverless v2 writer in us-east-1 can support the [RDS Data API](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.Aurora_Fea_Regions_DB-eng.Feature.Data_API.html). The HTTP endpoint is currently a separate opt-in Terraform change. [A Data API read resumes a paused writer](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html), so browsing can incur Aurora compute and the page does not promise a zero-cost read. The Lambda has no VPC attachment, NAT or database socket and uses only `ExecuteStatement` on this cluster plus `GetSecretValue` on one dedicated reader secret. Its database role has column-level SELECT grants for this projection, no writes or raw payload access. The existing app/migration roles, batch schedule and two emails are unchanged. [Cognito Lite supports classic hosted UI and TOTP](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-sign-in-feature-plans.html); [API Gateway validates JWT issuer, audience and scopes](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html). Verify current account eligibility, region behavior, billing and MFA enrollment in a fresh account-backed review.

## Reviewed deployment sequence (owner actions, not executed here)

1. From the published revision, run local checks and a fresh remote-state Terraform plan with `enable_data_api=true` only. Confirm the plan changes the existing cluster's HTTP endpoint setting and leaves writer, scaling, deletion protection, schedule, task definitions, secrets and other resources untouched. Apply only that reviewed plan. Confirm the endpoint is enabled before provisioning a reader.
2. Install `boto3` in a private local Python environment. Supply `PAGE_CLUSTER_ARN` from `terraform -chdir=infra/terraform output -raw database_cluster_arn`, `PAGE_ADMIN_SECRET_ARN` from `terraform -chdir=infra/terraform output -raw managed_master_secret_arn`, and `PAGE_MIGRATOR_SECRET_ARN` from `terraform -chdir=infra/terraform output -raw migration_role_secret_arn` as environment variables. Run `python3 infra/page/prepare_reader.py` with the already configured `job-agent` AWS profile. This one-time script uses Data API and the managed administrator and existing migrator secret references; it generates a password in memory, sends only a SCRAM verifier in SQL, creates the separate `job_agent_page_reader` role and has the table-owning migrator grant column SELECT access and stores the password in a new Secrets Manager secret. It prints no password. The owner needs narrowly reviewed `rds-data:ExecuteStatement` on the cluster, `secretsmanager:GetSecretValue` on the managed master and migrator secrets and `DescribeSecret`/`CreateSecret` for the reader secret. If a role or secret already exists, or any step fails, stop and inspect both before a manual recovery; do not rerun blindly or rotate silently. The role/secret operation is not atomic across PostgreSQL and Secrets Manager.
3. In ignored local tfvars, set `enable_vacancy_page=true`, keep `enable_data_api=true`, add a unique `page_auth_domain_prefix` and the new reader secret **ARN** as `page_reader_secret_arn`; never put secret values or private profiles in Terraform. Review a fresh plan for Cognito Lite/TOTP, owner group, API Gateway JWT route, Lambda, its scoped IAM/logging and the existing cluster. Confirm no unrelated batch or DB changes. Apply only after review.
4. Privately create one Cognito user, enroll required TOTP and assign the user to `job-agent-owner`. Open `terraform -chdir=infra/terraform output -raw vacancy_page_url`; verify unauthenticated `/vacancies` is denied, a signed-in non-owner is denied, and the owner sees separate DE/AT pages, pagination, an empty state and only HTTPS links. Check Lambda responses/logs without printing tokens, profile contents or vacancy bodies. Observe whether Aurora resumes and later returns to 0 ACU. The page is AWS-unverified until these checks pass.

To stop data access without deleting the protected user pool, set `page_access_enabled=false` and review/apply a fresh plan that removes only the protected API route. This does not stop an in-flight read, delete the reader role/secret or disable Data API. Full cleanup requires a separate reviewed plan and explicit handling of Cognito deletion protection, the reader credential and the HTTP endpoint; never use broad destroy against the foundation. Lambda/API Gateway/Data API calls, Cognito active users, logs, Secrets Manager and Aurora wake time are potential cost drivers, not a measured bill or hard cap.
