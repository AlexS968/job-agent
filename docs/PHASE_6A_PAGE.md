# Phase 6A: protected vacancy page and source yield

Phase 6A.1 is deployed: the owner signed in, loaded the protected DE/AT page and opened an original posting link. The first vacancy request failed and a later request succeeded; its cause is unknown. This is observed behavior, not evidence that Aurora wake-up caused the failure. The shell and OAuth configuration are public assets; vacancy data requires an API Gateway JWT access token and membership in the `job-agent-owner` Cognito group. Cognito Lite uses its classic hosted UI, a password and required TOTP. The browser uses authorization code with PKCE, keeps its access token only in memory and does not log or store profile JSON. The API also checks owner-group claims. No signup route is provided.

The page switches between `alex-de` and `alex-at` and reads current `rules-v1` evaluations. It shows suitable and needs-review preferred/reserve roles, an employer name, original HTTPS posting link, explicit reason codes and unknown conditions. It excludes synthetic source namespaces, stale source snapshots and unmatched roles, matching the existing report shortlist's trusted-source boundary. Only the newest registered version per profile is shown; if its sweep is incomplete, older-version rows are not mixed in. A profile without evaluated vacancies shows an empty list. This is a stored-evidence view, **not** a fresh evaluation, a country-permission confirmation, a new source of truth or a claim of personal suitability. Pages are capped at 20 rows, offset at 1,000 and JSON at 64 KB. Larger result sets require a later reviewed pagination design.

The existing Aurora PostgreSQL 17.11 Serverless v2 writer in us-east-1 supports the deployed Data API. [A Data API read can resume a paused writer](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html), so browsing can incur Aurora compute and the page does not promise a zero-cost read. The Lambda has no VPC attachment, NAT or database socket and has `ExecuteStatement` on this cluster plus `GetSecretValue` on one dedicated reader secret. The reader role has column-level SELECT grants, no writes or raw payload access. The existing app/migration roles, batch schedule and two emails remain.

## Historical Phase 6A.1 deployment sequence

1. **Observed partial state, not a fresh deployment:** Data API is enabled. The first local attempt failed before mutation because older boto3 could not resolve `aws login`. The second attempt created `job_agent_page_reader` and granted CONNECT/schema USAGE, then stopped at its first table grant because the migrator secret contained only `password`; Data API requires `username` too. Metadata-only checks found no reader-secret resource and no `source_items` SELECT grant. Do **not** run the previous script again. The reviewed recovery script first checks account, cluster, reader-secret absence, migrator-secret shape, table ownership and the reader's effective privileges. It accepts an absent role or a role with only a subset of its exact planned grants. Unexpected roles, privileges, account/cluster or secret state stop before mutation.
2. On the published, reviewed revision, establish the `job-agent` AWS CLI login session and privately set `PAGE_EXPECTED_ACCOUNT_ID` to the approved 12-digit account ID. Set `PAGE_CLUSTER_ARN`, `PAGE_ADMIN_SECRET_ARN` and `PAGE_MIGRATOR_SECRET_ARN` from the corresponding `database_cluster_arn`, `managed_master_secret_arn` and `migration_role_secret_arn` Terraform outputs (ARNs only). Then run exactly `python3 infra/page/prepare_reader.py` from the repository root. Its [AWS CLI `export-credentials` process bridge](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html) captures temporary credentials in memory for older boto3; never run or paste that export command directly in a terminal or log. It rejects credentials with under five minutes remaining. The script creates no credential file and writes no database password to a file, shell argument, Terraform state or output; the AWS CLI can maintain its own normal login cache.
3. **Review these exact mutations before step 2:** one new `AWSCURRENT` version of the existing migrator secret adds `username: job_agent_migrator`, preserving its existing `password` and all other fields. The ECS `password` reference remains valid. The script verifies that Data API then authenticates as the table-owning migrator. In the observed partial state it generates a new password in memory and rotates `job_agent_page_reader` because the earlier password was never saved; a fresh state would create that role instead. The administrator grants CONNECT/schema USAGE and the migrator grants only the page query's required SELECT columns. After a metadata-only privilege check, the script creates the separate reader secret. The role and secret operations are not atomic across services. Review permissions for STS caller identity, RDS cluster metadata, Data API `ExecuteStatement` on this cluster, `GetSecretValue`/`PutSecretValue` on the migrator secret, `GetSecretValue` on the managed-admin secret and `DescribeSecret`/`CreateSecret` for the reader secret; there is no broad secret or cluster access in the page Lambda.
4. After the script reports success, verify **metadata only**: compare `aws --profile job-agent --region us-east-1 sts get-caller-identity --query Account --output text` with the approved account; inspect `aws --profile job-agent --region us-east-1 secretsmanager describe-secret --secret-id "$PAGE_MIGRATOR_SECRET_ARN" --query VersionIdsToStages` for the new `AWSCURRENT` and retained prior version; and inspect `aws --profile job-agent --region us-east-1 secretsmanager describe-secret --secret-id job-agent-p5a-page-reader --query '{ARN:ARN,VersionIdsToStages:VersionIdsToStages,DeletedDate:DeletedDate}'`. Use an admin-secret Data API **read-only privilege query** such as `SELECT has_column_privilege('job_agent_page_reader','public.source_items','id','SELECT'), has_column_privilege('job_agent_page_reader','public.source_items','raw_payload','SELECT'), has_table_privilege('job_agent_page_reader','public.vacancies','DELETE')` and require true/false/false. Do not call `GetSecretValue` to display either secret, print SQL results containing vacancy data, or paste credentials into reports.
5. A failed or interrupted run requires metadata review before retry. If only the migrator version changed, the repaired script recognizes its correct `username` and does not create another version. If the reader secret is absent and role privileges are an exact subset of planned grants, a reviewed rerun rotates the unsaved reader password again and resumes grants. If the reader secret exists or privileges are unexpected, the script refuses a rerun; investigate manually rather than deleting, overwriting or rotating it. A lost secret-creation acknowledgement is ambiguous. If the migrator secret version update itself is uncertain, compare version stages and stop on any other secret change. Do not roll back the migrator secret by blindly restoring `AWSPREVIOUS`: preserve its password and verify both ECS and Data API consumers before any reviewed reversal.
6. In ignored local tfvars, set `enable_vacancy_page=true`, keep `enable_data_api=true`, add a unique `page_auth_domain_prefix` and the new reader secret **ARN** as `page_reader_secret_arn`; never put secret values or private profiles in Terraform. Review a fresh plan for Cognito Lite/TOTP, owner group, API Gateway JWT route, Lambda, its scoped IAM/logging and the existing cluster. Confirm no unrelated batch or DB changes. Apply only after review.
7. Privately create one Cognito user, enroll required TOTP and assign the user to `job-agent-owner`. Open `terraform -chdir=infra/terraform output -raw vacancy_page_url`; verify unauthenticated `/vacancies` is denied, a signed-in non-owner is denied, and the owner sees separate DE/AT pages, pagination, an empty state and only HTTPS links. The owner verified sign-in and a successful protected vacancy read; the first failed read remains undiagnosed. Other checks in this historical procedure must not be inferred from that observation.

To stop data access without deleting the protected user pool, set `page_access_enabled=false` and review/apply a fresh plan that removes only the protected API route. This does not stop an in-flight read, delete the reader role/secret or disable Data API. Full cleanup requires a separate reviewed plan and explicit handling of Cognito deletion protection, the reader credential and the HTTP endpoint; never use broad destroy against the foundation. Lambda/API Gateway/Data API calls, Cognito active users, logs, Secrets Manager and Aurora wake time are potential cost drivers, not a measured bill or hard cap.

## Phase 6A.2 local change and reviewed rollout

V18 adds a `country-v1` interpretation to each stored evaluation. Only a dedicated Greenhouse or Lever posting-location field matching the normalized current source snapshot can confirm DE or AT: explicit country names, Berlin for DE and Vienna/Wien for AT are recognized. Generic remote/EU wording and a 12-week work-abroad allowance remain unknown. This is evidence of a posting location, **not** independently verified legal work authorization. Historical rows default to UNKNOWN; the next normal evaluation sweep refreshes them in its existing per-vacancy transaction. Page and report shortlists both require `CONFIRMED`; unknown and excluded rows remain in stored evaluations and diagnostics. No historical result is deleted. A source snapshot change makes an older evaluation ineligible for the current view. The current page query cannot independently recompute a normalized-content revision if that content changes without a new source snapshot; a full sweep is required after such a change.

The protected `/yield` route shows each active verified source for both current DE/AT profile versions. Observed is distinct listing IDs across all stored source observations; stored is distinct linked vacancy IDs, including cross-source links. Evaluated, shortlisted, excluded and unknown-condition counts are attributed only to the current evaluation's actual source-item namespace, not every source linked to that vacancy. Shortlisted means role-relevant SUITABLE/NEEDS_REVIEW with confirmed country location. Excluded, unmatched-role, country-unknown and unevaluated counts are shown separately, with exclusion reason and unknown-condition counts. Loss categories may overlap and must not be added. Stored-vacancy counts can overlap between sources; one vacancy can also be evaluated for both profiles. The cross-source overlap count identifies linked vacancies shared by active sources. The window is all stored history as of each read, not the complete platform or a country-wide job market. These counts cannot explain why the owner did not apply before feedback exists. Both `/vacancies` and `/yield` require JWT authorization and the owner group; responses are capped and paginated. The selected country is visually marked. A failed vacancy read offers a manual bounded retry; its message does not infer a cause.

After review and publication, first apply V18 with the reviewed migrator task. With the existing `job-agent` login, set `PAGE_EXPECTED_ACCOUNT_ID`, `PAGE_CLUSTER_ARN` and `PAGE_MIGRATOR_SECRET_ARN` from the approved account and Terraform outputs as in the historical sequence. Run `python3 infra/page/upgrade_reader.py` once: it checks account, cluster, existing reader secret and exact old/partial grants, then adds only source identity, V18 interpretation and active-registry SELECT columns. It changes no password or secret version; on interruption, inspect metadata and rerun only after confirming the state is still an allowed subset. Verify column privileges with metadata-only Data API queries; `source_items.raw_payload` and write privileges must remain denied. Review a fresh Terraform plan: it should add the protected JWT `/yield` route and update page Lambda code, without changing the schedule, two emails or existing database. The Java image containing V18 and the shared country interpretation can be published together with a later reviewed Phase 6A.3 image. Until V18, reader grants, a new evaluation sweep and page Lambda are deployed, the Phase 6A.2 behavior is **local only**. Verify DE/AT separation, Berlin absent from AT recommendations, explicit eligible examples, diagnostics, auth denial, pagination, retry UX and the next scheduled report selection in AWS before claiming cloud acceptance.
