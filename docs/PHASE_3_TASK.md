## Delivered boundary

An explicit `--mode=greenhouse` reads at most three configured public Greenhouse boards using the official unauthenticated Job Board GET endpoint with `content=true`. It stores each published post's raw JSONB, original URL, fetch time, source update time, description, normalization version and content digest. The adapter never calls application submission endpoints. Board tokens and employer display names are configured via `GREENHOUSE_BOARDS`; each name must be verified against the employer's public board metadata. Employer identity is `greenhouse-board` plus board token. Vacancy identity is board-scoped namespace plus job-post `id`, not `internal_job_id` or display name. A changed display name for the same configured token currently conflicts with the existing employer row and needs explicit review; the adapter does not guess whether a rename or board transfer occurred.

The adapter validates the full response before any listing transaction. It accepts at most 300 posts and 4 MB, with three attempts per board, 3-second connection timeout, 8-second request timeout, 9-second overall wait and a cumulative four-second retry-wait budget per board. Valid `Retry-After` delta-seconds and HTTP-date values are honored in full if they fit the remaining budget; longer delays fail the board before another request. Malformed values use bounded local backoff. The retry-wait budget does not include request time, which has separate timeouts. Transport errors, 429 and 500/502/503/504 retry; 404, invalid configuration, malformed or oversized responses do not. Thus a configured invocation issues at most nine GET requests. The [official Job Board API](https://docs.greenhouse.io/job-board.html) does not publish a requests-per-second allowance; no such limit is assumed. Normal startup does not fetch.

Each listing has a separate service-owned transaction. The run row starts outside it; source snapshot, current employer/vacancy state, provenance link, pending event and `SUCCEEDED` transition commit together. Its result distinguishes `CREATED`, `UPDATED`, `UNCHANGED` and `STALE`; synthetic runs retain `INGESTED`/`REPLAYED`. A failure rolls these writes back; `FAILED` is then recorded in a separate transaction. Calls with an ambient transaction are rejected before run creation. Failure-tracking errors are suppressed beneath the original exception. Database unavailability before run creation and process crashes may leave no failed run or a `RUNNING` run. Board fetch errors have no listing run. Successful listings remain committed if another listing fails; invalid/conflicting listings are rejected while later listings may continue. Unexpected processing/database failures stop the remaining work to avoid repeated failing writes. Invocation counters describe attempted work, and fetched posts may exceed processed posts. Any rejected or failed work makes the batch exit nonzero. A stale older version is a successful unchanged no-op.

The content digest uses recursively sorted JSON object keys and excludes only the top-level `updated_at`. Fetch time never affects it. Source snapshots are identified by board/post/source version. The vacancy service makes stale, equal, conflicting, unchanged and updated decisions after the repository locks the current row, in the same ingestion transaction as source and outbox writes. The unique listing constraint arbitrates first-insert races. Equal timestamps with different content conflict and roll back. Older versions cannot overwrite newer current state. Newer equal content advances the version without another event. Newer changed content atomically updates the vacancy and emits `VacancyUpdated` v1; first creation emits `VacancyDiscovered` v1. Both event envelopes retain existing type/version/run/vacancy identity and minimal `vacancy_id` payload. The local consumer records one receipt per event and creates its one observation only for discovery. A retry cannot duplicate its database effect. No closure is inferred from a missing post; absence reconciliation is deferred. Unknown location, compensation, remote arrangement and eligibility remain unknown. Source HTML is retained only as untrusted data.

## Phase 3B: Lever site ingestion (merged)

`--mode=lever` accepts up to two `LEVER_SITES` entries in `global|site|verified name` or `eu|site|verified name` form. The [official Lever Postings API](https://github.com/lever/postings-api) documents the global and EU hosts, `mode=json`, `skip`/`limit` pagination, posting `id`, `text`, `hostedUrl`, `applyUrl`, categories, descriptions and structured sections. The public response observed in the smoke test contained `createdAt`, but the official field list does not document a listing update timestamp equivalent to Greenhouse `updated_at`. The GET reference does not grant application-submission authority or publish a request-rate/completeness guarantee. The adapter makes only GET requests to fixed official hosts and never fetches application URLs.

Shared bounded transport retains a three-second connection timeout, eight-second request timeout, nine-second overall wait, 4 MB response ceiling, cancellation and no redirects. Per site: four pages of 50, three attempts per page, four seconds cumulative retry wait; at most two sites, 24 requests and 400 listings per invocation. A full fourth page fails explicitly. HTTP 429/500/502/503/504 and transient transport errors retry; 404, malformed response and oversized response do not. Valid `Retry-After` delta-seconds or HTTP-date is honored in full when it fits the remaining wait budget; otherwise the site fails before another request. No live source is required by CI.

Employer identity is Lever region plus site; vacancy identity is Lever region, site and posting ID. Display name alone never merges identities, nor are Lever and Greenhouse postings merged by title. V5 adds `source_items.apply_url` and `vacancies.observation_started_at`. Raw JSONB retains description, opening, lists and additional sections; `description` is copied into the existing normalized description column. Unprovided facts remain null/unknown. The entire source response is validated outside a database transaction. One listing gets one run and one service-owned transaction for source snapshot, employer/vacancy, provenance, optional outbox event and success transition. First content creates `VacancyDiscovered`; later changed content creates `VacancyUpdated`; same content does not emit an event. Runs fail separately after rollback; a fetch failure creates no listing run. The batch reports per-invocation counters and exits nonzero on rejected or failed work, retaining earlier committed listings.

Lever lacks a reliable update version, so the adapter captures observation start before its first HTTP request. The ingestion service truncates that Instant down to PostgreSQL microsecond precision once, before persisting source/vacancy rows; the vacancy service requires this precision and compares the stored value under a row lock. A delayed observation from an older microsecond slot is stale even when committed after a later one. Distinct observations in the same slot are equal-time: identical content is unchanged, but conflicting content is rejected and rolled back rather than resolved by arrival order. A later slot with identical content advances the watermark without a new snapshot/event. The content digest canonicalizes JSON object-key order and excludes observation time. This is local ordering at microsecond precision, not a source-provided version, a total order within a microsecond or a guarantee that every source change was seen. Missing postings are not closed. Concurrent insert races use database unique constraints.

On 2026-10-22, the public `global|mashgin|Mashgin` site returned 14 posts in one request. In disposable localhost PostgreSQL 17.11, first explicit run created 14 vacancies/events; second run made one request and reported 14 unchanged. Aggregate counts: 14 snapshots, 14 vacancies, 14 pending events, 28 successful runs. The container was removed; no live response fixture was committed. Local `./mvnw -B clean verify` passed 27 unit and 69 PostgreSQL/batch integration tests, with zero failures/errors/skips. The five added PostgreSQL regressions cover sub-microsecond replay, a rounding boundary, same-slot unchanged/conflicting content and stale observation ordering. JaCoCo covered 103/112 lines and 61/88 branches in `LeverSourceAdapter`, 58/63 lines and 32/54 branches in `LeverIngestionService`, and 58/63 lines and 21/34 branches in `LeverBatchService`. These whole-class measures are not Sonar new-code coverage. PR #9 build and Sonar checks later passed; its separate main-push Sonar job failed. Broad verified employer discovery, cross-source reconciliation, absence reconciliation, evaluation, cloud delivery and application actions remain future work.

## Phase 3C.1: Bounded Tavily candidate discovery (merged)

The explicit `search-dry-run` mode lists four `pilot-v1` queries without a key or network access. `search-pilot` uses Tavily Search Basic only, with a fixed endpoint and explicit cost-related settings. V6 permanently caps reserved outbound attempts at 100 across workers/restarts; each invocation is capped at 12 and each query at three. A reservation commits before HTTP and remains counted after a crash or ambiguous response. Provider-reported credits are separate from local attempts. No PAYGO, payment method, candidate fetching, source activation or LLM integration is part of this increment. Candidate URLs are transient and marked `UNVERIFIED`; full responses and snippets are not persisted. [ADR 0003](adr/0003-tavily-search-pilot.md) records the dated provider basis and retention uncertainty.

Phase 3C.2 adds explicit candidate verification against an owner-confirmed or independently reviewed official domain, bounded SSRF-safe fetching, an idempotent evidence/identity registry and separate activation before existing source adapters import. See [ADR 0004](adr/0004-source-verification-registry.md). The previous pilot did not persist its candidates; this increment accepts explicit URLs without another search request. A technical ATS association is not employer fit, Germany hiring eligibility or permission to apply. Offline tests use synthetic HTTP responses and PostgreSQL. On 2026-10-26, a bounded live smoke used the independently reviewed [Mashgin career page](https://www.mashgin.com/careers), whose direct jobs link leads to `jobs.lever.co/mashgin`. Each of two explicit verification runs used one GET and returned `VERIFIED` for `LEVER/global/mashgin` in a disposable PostgreSQL 17.11 database. The second run left one source and one evidence row; zero sources were active and zero vacancies imported. The container was removed. This does not verify the prior 34 Tavily URLs or assess role fit. Normal CI uses synthetic HTTP only.
