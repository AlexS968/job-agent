## Why PITR and prerequisites

[Aurora PITR](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-pitr.html) creates a new cluster without changing the source. It uses the source's continuous automated backups and a time within the reported `EarliestRestorableTime`–`LatestRestorableTime` interval. A snapshot restore would require a confirmed existing snapshot and demonstrate recovery only at its snapshot time. The source retains automated backups for **one day**; neither yesterday's timestamp nor a current snapshot is assumed available. Choose an explicit UTC restore time strictly within the observed interval. Capture the source `agent_runs` count and migration status read-only at a time consistent with that restore point; if the source changes, the count is no longer a reliable reference. The existing cloud evidence is `agent_runs=0`, so a zero-count match tests limited recovery. A synthetic marker would strengthen the drill but requires a separate reviewed source-data write *before* a future backup; this drill does not add it or emit any business event.

Before planning, confirm the source cluster is `available`, one-day retention, its reported earliest/latest restorable times, Aurora PostgreSQL version, encryption key, DB subnet group, parameter group, 0–2 ACU scaling, 300-second pause and a current automated-backup window. Confirm the app secret ARN and its credential still authenticate at the selected restore point; rotation after that point can prevent verification. Confirm `job_agent_app` existed at that time. SQL role definitions and password verifiers are database state, but Secrets Manager credentials are external to the backup. The behavior of a restored RDS-managed master secret is **not assumed**. The drill uses neither the source master secret nor administrator access; inspect restored `MasterUserSecret` metadata separately. If application authentication fails, stop and review credentials rather than retrieving a master value or modifying the restore.

AWS [PITR API](https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_RestoreDBClusterToPointInTime.html) supports explicit subnet group, security groups, parameter group and Serverless v2 scaling; these are specified because defaults can weaken the network/TLS configuration. The [AWS provider 6.71.0 cluster resource](https://raw.githubusercontent.com/hashicorp/terraform-provider-aws/v6.71.0/website/docs/r/rds_cluster.html.markdown) supports `restore_to_point_in_time` with `restore_to_time` and `full-copy`. The restore configuration explicitly selects the source's private subnet group, force-SSL cluster parameter group, encrypted Aurora source storage, separate verifier-only security group, 0–2 ACU and 300-second auto-pause. A separate private `db.serverless` writer is necessary. Verify effective encryption, KMS key, parameter status, credentials and auto-pause after creation; source inheritance alone is not evidence. No source endpoint or application task definition changes.

Cleanup **by the four-hour deadline**, even if verification fails: set only `enable_restore_drill=false` in the ignored drill tfvars, generate a **new** `terraform -chdir=infra/terraform plan -input=false -out=phase5-restore-cleanup.tfplan`, review that deletion addresses only the uniquely tagged drill resources and task definition, then apply the reviewed cleanup plan. Do not use `terraform destroy`, target the source, disable source protection, edit state or reuse an earlier saved plan. Review whether automatic backups, snapshots, a restored managed secret, task revisions or logs remain; delete only separately identified drill artifacts after approval. Source roles/secrets and endpoints remain.

## Cost and limits

Planning estimate in us-east-1 before credits: one temporary Aurora cluster at up to **2 ACU** for four hours is at most about **$0.96 compute at $0.12/ACU-hour** if active continuously at that configured maximum; 10 GB full-copy storage for four hours at $0.10/GB-month is about **$0.006**, plus charged I/O, backup/snapshot storage outside allowances, data transfer and CloudWatch logs. One 15-minute 0.25-vCPU/0.5-GB Fargate verifier is about **$0.003**, plus roughly **$0.001** public IPv4. These are illustrative rate calculations, not a billing cap; actual storage, restore duration and I/O are unknown. If cleanup fails and 2 ACU remains active for 730 hours, compute alone is about **$175/month**, plus storage and other usage. Auto-pause could reduce compute but is not guaranteed during a restore or failed drill. The four-hour cleanup deadline is an operational target, not an automatic shutdown. Credits and $5/$10 budget emails do not enforce a cap. Check current [Aurora](https://aws.amazon.com/rds/aurora/pricing/), [Fargate](https://aws.amazon.com/fargate/pricing/) and [public IPv4](https://aws.amazon.com/vpc/pricing/) rates before execution.
