## First direct-channel increment

The manual application mode `--mode=himalayas-intake` uses `/jobs/api/search?q=Java&sort=recent&page=1`. The three requests add `country=DE&exclude_worldwide=true`, `country=AT&exclude_worldwide=true`, and `worldwide=true` respectively. Each response may contain up to 20 rows, for at most 60 processed rows. The shared HTTP transport bounds connection time, request time, total response time and response size. It does not follow redirects. The mode neither retries a filter nor follows pagination. A failed filter is named in the summary with a safe outcome, and successful filters still import. The command exits nonzero for filter or row failures. A database failure stops the invocation and earlier committed work remains replayable.

Within `himalayas`, the canonical posting path from the public GUID identifies the vacancy. Filter overlap is collapsed before persistence, using the first valid row in the fixed filter order. Source snapshots retain the Himalayas posting URL and the original row, including advertised location, time-zone and employer fields. A posting-scoped unverified employer placeholder allows intake before employer association. The channel does not create an employer-board association or merge another channel's vacancy by title or employer name. An unchanged replay reuses the snapshot and adds no outbox event. Changed evidence updates the vacancy under the same identity. The first-stage assessment and any vacancy event commit in the existing ingestion transaction.

The summary reports requests, fetched rows (including repeated and invalid rows from accepted pages), distinct valid posting identities, persisted role candidates, created/updated/unchanged vacancies, failed rows and named failed filters. These are sample counts. The provider's advertised total is not used. The existing `--mode=evaluate-rules` and `--mode=shortlist` commands support review. Shortlist output identifies Himalayas and shows the original posting link plus the validated HTTPS `applicationLink` separately as the Apply link when available. A stored positive Unix-second `expiryDate` excludes the posting from active review and shortlist at or after that time, including on later reads without another import. Missing or invalid expiry stays unknown. The source history and evaluations are retained. Search filters, country lists and remote labels do not confirm DE/AT work eligibility. Himalayas remains a review source outside the protected country recommendations.

## Historical Tavily discovery and trust boundary

The existing Tuesday/Thursday scheduled task calls `BatchPipelineService`, which runs discovery **before** its one bounded active-source import, outbox publication, queue consumption, DE/AT evaluation sweeps and combined report. The explicit `--mode=source-discovery-once` runs the same bounded discovery and import services without SQS or report publication; it fails if the discovery gate is disabled. The existing `--mode=batch-pipeline` also remains a bounded one-off full batch. Discovery is disabled by default. When enabled, four fixed `source-coverage-v1` Tavily Basic queries cover Germany and Austria, Java/Spring backend work, and generic Backend/Software Engineer titles. Each requests at most ten results. Direct ATS leads can trigger one extra `source-coverage-evidence-v1` Basic query for up to three possible employer pages per distinct board in that invocation. Primary queries, evidence lookups and retries share the **12-request invocation cap** and V22's **120-request UTC-month cap**. Links are leads, not verified employers or vacancies.

V21 preserves canonical result URLs, first/last search-attempt provenance, source-import rotation and versioned candidate assessments. V22 adds a UTC-calendar-month reservation ledger, token-fenced discovery claims and an automatic-v2 evidence-request count bound of 45; the earlier manual verifier remains capped at three requests per attempt. The historical 100-attempt pilot ledger and records are retained; recurring reservations use a separate 120-request monthly cap. Each attempt uses the UTC month at reservation time, including across midnight during a run. The guarded monthly increment and attempt row commit together before HTTP, including for a retry. Neither a timeout nor a crash refunds an attempt. Concurrent workers share the cap. A reached monthly cap sends no further Tavily request; already stored leads can still be processed. Provider-reported credits and actual billing remain separate from local reservations.

V23 classifies retained and new URL leads by exact host/subdomain and board path: Greenhouse/Lever URLs are first-priority `ATS` leads only when the parser extracts a valid board identity. An ATS-host homepage or malformed board path is retained as `MANUAL_REVIEW/NON_EMPLOYER_SITE` without using a fetch slot. Other categories are plausible employer hosts, known job aggregators (`linkedin.com`, `indeed.com`, `glassdoor.com`, `wellfound.com`, `remotefront.com`, `devjobs.de`, `devjobs.at`), and separate vendor/tool sites (`greenhouse.com`, `tavily.com`). ATS leads precede employer-hosted leads; each class remains ID-ordered under token-fenced `FOR UPDATE SKIP LOCKED` claims. Aggregator-only leads remain in the ledger as `MANUAL_REVIEW/AGGREGATOR_ONLY_LEAD`; vendor/tool leads also use `NON_EMPLOYER_SITE`. Neither consumes the five fetch slots. The exact-host/subdomain match does not block lookalike employer domains. This classification is only a scheduling hint: it neither verifies a source nor rejects an employer because its listing title lacks Java. Other unfamiliar hosts remain eligible for the normal independent-evidence check. The four recurring queries are unchanged: the first five checked IDs do not establish the mix of all 35 stored leads, so a query rewrite would be speculative.

Each invocation claims at most five due leads. For an employer-hosted result, including an individual vacancy URL on another path, the SSRF-safe verifier checks the host's homepage, follows at most three same-host careers links selected by path or label, and requires one unambiguous Greenhouse/Lever board identity. A same-host redirect or an employer careers-page redirect directly to a supported ATS board can supply association evidence; an unrelated cross-host redirect cannot. For a direct Greenhouse/Lever vacancy or board result, a bounded Basic evidence query proposes up to three independent employer hosts. Each host must pass the same homepage-to-careers-to-ATS check, and the identity must match the original ATS board exactly. Multiple claiming domains, multiple board identities, unsupported/mixed links or incomplete fetches do not activate a source. The ATS slug and search text are only lookup hints. A per-invocation cache avoids repeating the evidence query for the same board and homepage checks for the same host; it does not persist trust across runs. The homepage and at most three careers pages each have a five-second fetch budget, three same-host redirect requests, a 256 KiB response limit and 200-link inspection limit. Fetches and Tavily calls happen outside database transactions; short transactions fence and record the claim, verification evidence, registry decision and activation. A newly inserted, conflict-free verified association is activated immediately. An existing inactive association is **not** silently reactivated. Missing/unsafe evidence remains inactive with machine-readable reasons for exceptional manual review. Fetch failures and request-cap deferrals wait 30 minutes before retry, at most three claimed attempts; expired claims are fenced and exhausted work becomes `MANUAL_REVIEW`. A homepage/careers link chain supports a domain-to-board association, but cannot prove legal employer ownership or cover boards absent from search results.

`--mode=review-discovery` provides bounded diagnostic pages of stored leads and reasons. `verify-discovery`, `verify-source` and `activate-source` remain exceptional owner-reviewed recovery tools, not ordinary steps for every search result. Search snippets and employer names alone never activate a board. The existing source-identity, freshness and conflict watermarks still apply. Active-source import rotates through at most five sources per invocation and retains per-board fetch limits; it need not revisit every source on each scheduled run. An expired import claim can be reclaimed, while the database's stable identities prevent duplicate vacancy rows.

After import, at most 100 current, linked, previously unassessed non-synthetic snapshots receive a `java-backend-candidate-v2` decision. A generic engineering title proceeds to description evidence; clear Java/Spring backend evidence advances, unrelated professions do not, and unclear or other-stack evidence stays `REVIEW`. Kafka and other unconfirmed owner skills do not exclude a Java-first role. The stored assessment is linked to source snapshot and vacancy. Current trusted-source `rules-v2` evaluation reads that assessment; existing `rules-v1` evaluations, receipts and extraction evidence remain historical. DE/AT eligibility and salary uncertainty remain separate. The protected page requires current `rules-v2` evaluations after the profile sweep.

Per-run logs distinguish searches attempted, outbound requests, distinct returned lead URLs, confirmed/activated/review/retryable associations, imported listings, newly assessed candidates/review/other roles and DE/AT recommendation counts. Each attempted verification logs lead ID, stage, normalized host, HTTP status when available, redirect/request counts, elapsed milliseconds, retryability, outcome and reason; the link-limit reason includes actual and allowed link counts. URLs, query strings, bodies and credentials are omitted. HTTP 429/5xx remain bounded retries; HTTP 4xx such as 403/404 become review outcomes without automatic retries. These are **invocation counts**, not a claim about all currently stored vacancies or market coverage. A board's fetched listing count includes irrelevant roles; a URL lead is not a listing; one vacancy can have multiple source snapshots or appear for both profiles. Phase 9A.2 will use stored provenance and deduplicate vacancy identities for its protected report.

The initial AWS run checked IDs 1–5 in ID order: `careers.telekom.com` and `remotefront.com` had generic `HTTP_STATUS` failures; `wellfound.com` exceeded the link limit; `in.linkedin.com` lacked independent employer evidence; and `en.devjobs.de` had a generic `HTTP_STATUS` failure. The old diagnostic did not retain the status codes, so those failures cannot be classified retrospectively. This local follow-up does not establish that any of the remaining leads is verifiable. A separately approved controlled AWS run must activate a new conflict-free source and import its vacancies before Phase 9A.1's live acceptance criterion is met.

The application rejects a missing or stale review date (over 30 days). This is an owner-attested operational gate, **not** programmatic evidence of account billing settings. Do not enable it if the settings or retention rights are unresolved. No paid call was made in this increment.

Official [Tavily credit documentation](https://docs.tavily.com/documentation/api-credits) lists Basic Search at one credit/request and PAYGO at USD 0.008/credit. At most 120 Basic requests therefore correspond to USD 0.96 at that rate; prefer the free 1,000-credit monthly Researcher allowance with PAYGO disabled. Application reservations do not impose a provider billing cap, and provider terms/prices may change. [Tavily platform terms](https://www.tavily.com/terms) require independently checking output; exact long-term URL-retention rights and the owner's account settings still require owner verification. Do not use Advanced Search, Extract, Crawl, Brave or an LLM here.

## Employer monitoring from stored vacancies

PR #69 integrated Himalayas into the existing Tuesday/Thursday batch. V28 adds a local employer-resolution step after that batch's normal imports and queue delivery, once before the two profile sweeps. It picks up previously stored and newly imported Himalayas postings and named LinkedIn cards, including repaired cards. Each pass screens up to 60 posting/name pairs with the existing candidate policy. It has two verification slots. One goes to the oldest due board renewal when available, and the remaining slots go to new or retryable leads. A generic engineering title with unknown stack can proceed to verification. The lead retains the vacancy ID, source item, posting URL and advertised name. Replays share that posting's lead. Equal names on different vacancies do not establish a common employer. The direct vacancy, evaluation and eligibility evidence remain usable independently.

A company website or application URL is a hint. The verifier checks the employer homepage for an exact case-insensitive site name (page title or Open Graph site name), then checks its careers link and board identity. Supported evidence includes ordinary Lever posting links and Greenhouse board links or static iframe/script embeds, including European embed hosts with one valid board token. The verifier reads markup without executing scripts. A supplied ATS identity must agree with the official site. If there is no employer host, or the hinted site does not identify the named company, a targeted Basic search may propose up to three sites. Search requires the existing reviewed billing gate and shares the remaining 12 attempts per invocation and 120 per UTC month with the original discovery flow. A failed search-result host does not prevent checking the next host. One independently confirmed match can proceed. Conflicting board or employer evidence still requires review. Without a match, a transient fetch failure takes precedence over an unrelated negative result. A disabled or exhausted search gate leaves a waiting lead. It does not justify activation.

Only a conflict-free association enters the existing verified-source registry. Newly verified boards become eligible for the next bounded five-source rotation. Automatically activated boards become due for recheck after 21 days. The verifier fetches the stored official careers page within the batch deadline, without a search. Only the same board identity refreshes the 30-day freshness window. A failed fetch leaves the old verification timestamp intact and defers another check for at least a day. A changed board goes to review. An expired board stops polling and requires reviewed activation after fresh verification. An inactive board stays inactive. Stale or unreachable boards remain visible in import diagnostics while committed work from healthy sources can still be delivered. Transient failures wait 30 minutes between attempts, up to three claimed attempts. Conflicting domains, unsupported careers pages and exhausted retries remain inspectable. The resolver uses the existing SSRF-safe fetcher and the remaining batch deadline. Sites without recognizable ownership or static careers evidence can remain unresolved.

For acceptance, compare lead states before and after a bounded batch, follow one verified lead to its registry row, then confirm a later import from that board created an attributed vacancy.
