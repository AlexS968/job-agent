## Initial Phase 7A implementation

The intake additionally stops before exceeding 100 recognized cards in one invocation; earlier message commits remain durable. It makes at most one list request and 20 full-message requests, plus one OAuth refresh, with fixed request and response limits. Optional `--after-date=YYYY-MM-DD` and `--before-date=YYYY-MM-DD` narrow a controlled search to historical archived alerts without changing their labels. A full first result page is **not** proof that older matching mail has been reconciled.

`--mode=linkedin-intake --max-messages=10` is an explicit, unscheduled read-only Gmail run (maximum 20 messages). It searches `jobalerts-noreply@linkedin.com` across inbox and archive regardless of read state or the old `LinkedIn Processed` label, excluding spam and trash; the parser checks the exact sender again. It reads one bounded Gmail result page; older history and final Sheet reconciliation belong to 7B. The Gmail [list API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) returns message IDs; [full message reads](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get) supply MIME parts. The subject's advertised number is never used as a card count. Supported direct LinkedIn job links in HTML anchors and plain-text MIME parts collapse by numeric job ID within a message. Unknown job links and missing supported MIME bodies are counted as unsupported. The parser does not follow tracking redirects or fetch job pages.

`gmail_alert_messages` stores Gmail message identity, observed-card count, unsupported count, `COMPLETE`/`NEEDS_REVIEW` and a bounded review reason. An individually malformed or unsupported alert records a review outcome and does not prevent later messages in the same invocation from being inspected; replay recognizes that outcome. Gmail transport and database failures remain retryable and stop the invocation. `gmail_alert_cards` stores one durable outcome per recognized job link. The entire valid message's source snapshots, vacancy links, outbox events, card outcomes, run success and completion marker commit together. An interrupted or failed transaction has no partial source/domain writes; run failure is tracked separately, subject to database availability. A repeated message is skipped. A repeated LinkedIn job ID in another message links a new source snapshot to the same vacancy; a link-only repeat retains an established title and emits no vacancy update, while a later real title can enrich a placeholder. The LinkedIn job ID is the vacancy identity. Employer identity is **not** inferred from email display text: an unverified placeholder is scoped to that job ID. Source records retain the Gmail message ID and time for provenance plus normalized public card title, canonical public link and job ID; private mail bodies and tracking parameters are not stored. Any `NEEDS_REVIEW` outcome remains visible in the final aggregate and the batch exits nonzero after processing the bounded list; no mailbox label is changed.

The page adds a separate owner-protected, paginated LinkedIn observation list. It is explicitly **not** the confirmed DE/AT shortlist or an email recommendation. A supported card location may advertise Germany, Austria, Remote Europe or Remote Worldwide; missing or ambiguous location remains `UNKNOWN`. Direction and a bounded location quotation are stored per card and shown separately from evaluation and work-country eligibility. This recognizes only explicit location text in supported card markup; other MIME layouts remain unknown pending controlled validation. The page reader gains SELECT on only the card source ID, direction and location evidence, not raw mail. A LinkedIn alert without verified employer, salary, stack, role or permanent work-country evidence stays unknown and visible for review. Existing rules-v2 evaluation can assess a Java/backend title; a generic title without description remains uncertain. The present private DE/AT profiles and confirmed-country result emails are unchanged. No alert label is promoted to work eligibility, and 7A does not claim confirmed recommendations in remote directions.

### Snapshot contract

The root fields are `workbook` (stable private Sheet ID), `timezone`, `captured_at` (ISO timestamp with offset), `previous` (null for rehearsal baseline, otherwise the latest checkpoint digest in that database), `status_map`, and `tabs`. The private, owner-reviewed status map translates exact source strings into OPEN, CONTACTED, APPLIED, CLOSED or ON_HOLD. Unmapped nonempty statuses require review. Original statuses and dates remain available in the stored document.

Each of `domestic_employers`, `international_employers`, `domestic_actions`, `international_actions` and `domestic_gaps` has the form `{"id":"original-tab-id","rows":[]}`. Export even empty tabs. Each row contains these fields (synthetic example):

```json
{"position":2,"key":"record-48","subject":"org-record-7","status":"Open","action":"","posting":"","cells":{"Employer":"Example Works","Date":"03/10/2026","Status":"Open","Source":"","Next action":""}}
```

Preserve **all** original columns in `cells` as strings, including empty values. Disambiguate duplicate column labels with their column letters. Preserve hidden links or formula targets in separate named cells alongside the original display text. Copy status, action and posting from the corresponding cells, using an empty string when absent. A website or role title alone gives no vacancy identity. The export mapping, status translations, row counts and any generated keys need private review against the actual Sheet.

* Use an immutable row identifier within its tab, or a privately reconciled stable key carried across exports. Never derive one from position or employer name. Missing keys use exact cell content for comparison and always require review. Duplicate keys retain every coordinate for review. An optional shared subject identifies a documented legacy employer record across tabs. Never construct it from name similarity.
* Employer records retain history. Exact LinkedIn, Greenhouse and Lever posting identities can link employer rows to an existing vacancy by source namespace and listing ID. Unmatched or unsupported postings require review. Action-list rows use the private review decisions below. Domestic gap rows remain research.
* Each snapshot commits atomically. A single writer lock and predecessor check protect against forks. Replaying the current document returns its stored report. Older snapshots cannot advance the head. Unique keys distinguish additions, edits and moves within a tab. One row may be edited and moved. Cross-tab moves or key replacements appear as removal plus addition and need manual reconciliation. Missing stable identity cannot prove an edit. Removed coordinates reference the predecessor and retain its full history.
* Each current row has one disposition per tab: IMPORTED, LINKED, UNCHANGED or REVIEW. Position-only moves of resolved rows are UNCHANGED. Changes to a link, review decision or status mapping are reclassified. Removed rows are counted separately. Inspect `sheet_reconciliation` by snapshot/tab/position for reasons, and `sheet_removals` for predecessor coordinates. Only aggregate counters and the snapshot digest are printed. An identical replay reproduces the original reconciliation totals with `replay=true`, including for checkpoints imported before action reviews were introduced.

### Private action review

Add an optional `action_reviews` object to the private snapshot. Within `domestic_actions` or `international_actions`, key each decision by the action row's stable `key`. Every decision includes nonempty `evidence` identifying the source or explaining the owner's judgment. This synthetic example links one historical record to a specific employer row:

```json
{
  "domestic_actions": {
    "synthetic-contact": {
      "kind": "LINK",
      "employer": {"tab": "domestic_employers", "key": "synthetic-employer"},
      "occurred_on": "2026-10-03",
      "supersedes_plan": "Contact if the role opens",
      "evidence": "The fixture records a dated contact after the conditional plan."
    }
  }
}
```

* `LINK` requires the employer tab and stable row key. `STANDALONE` preserves a historical action with no employer link. Both require historical action text in the source row's `action` field. `NOTE` preserves the original cells as a note or incomplete record without recording a historical action. It takes only `kind` and `evidence`.
* The source `action` field on employer rows represents the next step. On action-list rows it preserves historical text. The two values remain on their original records. For a linked historical event, use `supersedes_plan` only when evidence establishes that the dated event supersedes that exact conditional next step. Supply the verified `occurred_on` date as YYYY-MM-DD. Both source records and the rationale remain in the private snapshot. These fields create no application date, submission or outcome.
* Use an optional `event_key` for action rows that evidence identifies as the same historical occurrence. Incompatible dates, employer links or historical actions for that key require review. Distinct events may have different historical text, and different wording between a historical action and a next step is expected.
* Missing decisions and ambiguous row or employer keys remain REVIEW. References to absent rows or unsupported tabs reject the snapshot. A successful employer link reports LINKED with a null vacancy ID. Standalone actions and notes report IMPORTED and retain their kind in the private snapshot. Supply reviewed decisions explicitly with each new checkpoint. They apply to the listed legacy rows and do not carry forward to future postings or create live actions.
