## Local Phase 7A implementation (not cloud verified)

The intake additionally stops before exceeding 100 recognized cards in one invocation; earlier message commits remain durable. It makes at most one list request and 20 full-message requests, plus one OAuth refresh, with fixed request and response limits. Optional `--after-date=YYYY-MM-DD` and `--before-date=YYYY-MM-DD` narrow a controlled search to historical archived alerts without changing their labels. A full first result page is **not** proof that older matching mail has been reconciled.

`--mode=linkedin-intake --max-messages=10` is an explicit, unscheduled read-only Gmail run (maximum 20 messages). It searches `jobalerts-noreply@linkedin.com` across inbox and archive regardless of read state or the old `LinkedIn Processed` label, excluding spam and trash; the parser checks the exact sender again. It reads one bounded Gmail result page; older history and final Sheet reconciliation belong to 7B. The Gmail [list API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) returns message IDs; [full message reads](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get) supply MIME parts. The subject's advertised number is never used as a card count. Supported direct LinkedIn job links in HTML anchors and plain-text MIME parts collapse by numeric job ID within a message. Unknown job links and missing supported MIME bodies are counted as unsupported. The parser does not follow tracking redirects or fetch job pages.

`gmail_alert_messages` stores Gmail message identity, observed-card count, unsupported count, `COMPLETE`/`NEEDS_REVIEW` and a bounded review reason. An individually malformed or unsupported alert records a review outcome and does not prevent later messages in the same invocation from being inspected; replay recognizes that outcome. Gmail transport and database failures remain retryable and stop the invocation. `gmail_alert_cards` stores one durable outcome per recognized job link. The entire valid message's source snapshots, vacancy links, outbox events, card outcomes, run success and completion marker commit together. An interrupted or failed transaction has no partial source/domain writes; run failure is tracked separately, subject to database availability. A repeated message is skipped. A repeated LinkedIn job ID in another message links a new source snapshot to the same vacancy; a link-only repeat retains an established title and emits no vacancy update, while a later real title can enrich a placeholder. The LinkedIn job ID is the vacancy identity. Employer identity is **not** inferred from email display text: an unverified placeholder is scoped to that job ID. Source records retain the Gmail message ID and time for provenance plus normalized public card title, canonical public link and job ID; private mail bodies and tracking parameters are not stored. Any `NEEDS_REVIEW` outcome remains visible in the final aggregate and the batch exits nonzero after processing the bounded list; no mailbox label is changed.

The page adds a separate owner-protected, paginated LinkedIn observation list. It is explicitly **not** the confirmed DE/AT shortlist or an email recommendation. A supported card location may advertise Germany, Austria, Remote Europe or Remote Worldwide; missing or ambiguous location remains `UNKNOWN`. Direction and a bounded location quotation are stored per card and shown separately from evaluation and work-country eligibility. This recognizes only explicit location text in supported card markup; other MIME layouts remain unknown pending controlled validation. The page reader gains SELECT on only the card source ID, direction and location evidence, not raw mail. A LinkedIn alert without verified employer, salary, stack, role or permanent work-country evidence stays unknown and visible for review. Existing rules-v2 evaluation can assess a Java/backend title; a generic title without description remains uncertain. The present private DE/AT profiles and confirmed-country result emails are unchanged. No alert label is promoted to work eligibility, and 7A does not claim confirmed recommendations in remote directions.

### Private authorization and controlled rollout

1. In a private Google Cloud project, enable Gmail API and create a Desktop OAuth client authorized for **only** [`gmail.readonly`](https://developers.google.com/workspace/gmail/api/auth/scopes). The owner grants access through [desktop-app consent](https://developers.google.com/identity/protocols/oauth2/native-app); this is separate from Codex/old-pipeline Gmail access. Confirm Google consent/test-user and refresh-token lifetime requirements for the actual project before relying on a recurring run. No `gmail.modify` scope is requested.
   Keep the credential bound to one reviewed mailbox. Gmail message IDs are scoped to that mailbox; changing mailboxes requires a separate identity and reconciliation review, not a silent secret replacement.
2. Run the one-time local helper with private paths outside this repository: `python3 infra/gmail/authorize.py --client-file /private/path/desktop-client.json --output-file /private/path/gmail-intake-oauth.json`. It opens browser consent with PKCE and writes the refresh credential with mode 0600; it never prints its value. Securely create a dedicated Secrets Manager secret from that private file using an owner-reviewed process, then remove the temporary file after confirming storage. Put only the secret **ARN**, not its JSON, in ignored Terraform variables. Do not place the JSON in shell arguments, Git, logs or Terraform state.
3. After review/merge, publish one reviewed immutable application image for the shared Phase 7 release window and run migrations including V24 with the migrator role. Before enabling the changed page query, grant the existing reader only `SELECT (source_item_id, advertised_direction, direction_evidence) ON public.gmail_alert_cards` and `SELECT (fetched_at) ON public.source_items` through reviewed migrator Data API executions; verify those four column privileges and continued absence of raw-payload and write privileges. The source item `fetched_at` records the original email timestamp, so the page selects the newest email first and uses source item ID only to break ties. Do not rerun the initial reader bootstrap or rotate its secret. Fresh page-reader installs include the narrow grants in `prepare_reader.py`. Review a fresh Terraform plan with `enable_linkedin_intake=true` and the Gmail secret ARN. The optional task uses a dedicated execution role limited to its DB and OAuth secrets; it has no schedule, Gmail modify permission or SQS-send task permission. Review exact image digest, task definition, network, IAM and page route before apply. Existing scheduled batch and old writer remain unchanged.
4. In a separately authorized controlled run, start the output `linkedin_intake_task_definition_arn` once in the existing private task subnets/security group. Require exit 0 and inspect safe aggregate counters. Read-only SQL should reconcile `recognized_cards`, distinct `linkedin_job_id`, `COMPLETE`/`NEEDS_REVIEW`, `vacancies`, `source_items`, outbox events and page rows for the sampled message IDs. The protected page must show at least one LinkedIn-only source link and unknown country/other missing facts; it must not show it as a confirmed country recommendation. Repeat the same bounded sample and require no new vacancies, source snapshots, outbox events or user notifications. Review `NEEDS_REVIEW` messages separately. Stop all tasks and observe Aurora return to 0 ACU; do not infer that from a missing metric alone.

The first Gmail run has **not** happened. Gmail scope approval, actual MIME variants, private OAuth material, one-page sampling, page access and AWS task/secret behavior remain cloud acceptance dependencies. The result is not complete market coverage and does not reconcile old Sheet decisions.

Incremental cloud cost comes from the additional Secrets Manager secret, reviewed image storage, one-off Fargate runtime, Aurora wake time and logs. This local preparation neither measures a bill nor authorizes a recurring Gmail schedule. The existing scheduled result task and its two-profile processing remain unchanged.

If cloud acceptance fails, stop the one-off task, set `enable_linkedin_intake=false` in a newly reviewed plan and revoke the dedicated OAuth credential. Keep V24 history and source observations for reconciliation; do not reset the database or silently undo the old pipeline. The protected `/linkedin` route can be removed in a separate reviewed page rollback without changing existing `/vacancies` data.
